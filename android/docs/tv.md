# Dana TV (living-room TV, `tv` flavor)

`io.github.ronganam.dana.tv` ("Dana TV") replaces Google TV's home screen. Built and tuned on a TCL 75C7K (Google TV, Android 14, **32-bit armeabi-v7a**). Code is in `app/src/tv/` plus `app/src/wake/`. Build + install: `bin/deploy-tv.sh [-s SERIAL] [--debug] [--server URL]` (`--server` fills the pairing screen's address). The script grants `WRITE_SECURE_SETTINGS`, the `SYSTEM_ALERT_WINDOW` and TCL `AUTO_START` app-ops, enables the accessibility service and sets the home activity. adb: a TV that already trusts another adb key (e.g. Home Assistant's) needs it (`ADB_VENDOR_KEYS=<key> adb start-server`). Debug and release builds have different signatures, so switching between them needs an uninstall, which wipes settings and the pairing.

- **Pairing** (`TvPairingScreen`, shared logic in `main`: `data/pairing/`): until it is paired the TV opens on a pairing screen. The code from Dana's web Devices page ("Pair a device" → TV, where the room and role are chosen) is entered on an on-screen keypad of the code's 32 characters, so the remote's D-pad is enough (a keyboard's letters and Backspace work too); the server is picked from the Dana servers found on the home network (`_dana._tcp`, `data/discovery/`; one found fills the address) or typed (Up / Down leave the address field). `POST /api/pair {code, kind: "tv", name: <manufacturer and model>}` gives the TV its own device token, room and role (server `docs/devices.md`); the server and token go to `ServerConfig`, the device to `DevicePairing`. Settings → Connection shows the device (name · room · role, whose, the server; read back from `GET /api/devices`), **Test** (Home Assistant through the server) and **Unpair** (asks first; removes the device on the server with its own token, then back to the pairing screen).

- **TvHomeActivity** (HOME + LEANBACK_LAUNCHER): clock, favourite app banners, the Dashboard row (below), Home Assistant tiles (polled every 5 s while visible, through the server's `GET /api/ha/states?ids=` and `POST /api/ha/service`, so the TV holds only its own device token), camera snapshot tiles (`/api/camera/{entity}/proxy`), All apps, and Settings. Everything is customizable in Settings and stored as one JSON document (`TvConfig`, prefs key `tv_settings`; a fresh install starts from the site's `tv-defaults.json` in that shape, else a few common apps: `release.md` → Your site): apps and their order, HA entities (picker by domain via `?domains=`), cameras (RTSP URL plus snapshot entity), remote-button bindings (press the button to capture it; short and long press; actions: toggle camera PiP, open app, toggle entity, Ask Dana, home, Android settings), PiP corner and size, wake sensitivity, mic source and echo canceller. Intent extras: `--es server` (the pairing screen's address; ignored once paired), `--ez settings true`, `--ez assistant true` (opens Dana, like the Ask Dana button).
- **Dashboard** (`TvDashboardActivity`): the home screen's Dashboard row (one tile: "Open dashboard", with the TV's room or role) opens the TV's **own device dashboard** full screen in a WebView: `/dashboard?night=off` (server `docs/dashboard.md`; the Living room preset unless the role it paired with says otherwise; preset and widgets are chosen on the web, Devices → the TV → its dashboard). It signs in like the kiosk: the device token at `POST /login` for the session cookie (`data/network/WebSignIn`); a stale cookie is cleared and it signs in again, and a refused token forgets the pairing (back on the home screen, the pairing screen shows). `?night=off` because a TV has its own brightness (no light sensor, no `window.DanaKiosk`, so no Ask Dana button on the page: the wake word and the remote's Ask Dana binding work there as anywhere). The remote's D-pad moves between the page's focusable controls (light toggles, buttons; the WebView draws its focus ring) and scrolls when none is in that direction; controls that need touch are not focusable and are simply skipped. OK clicks, Back returns to the home screen. The native home (apps, Home Assistant tiles, cameras, PiP) is unchanged.
- **DanaKeyService** (accessibility service, key filtering): runs the remote bindings over any app. A short press acts on release; a long press acts after 550 ms, decided from the event's own timestamps. Bound keys lose their original function. It also hosts the camera PiP. No default bindings (a `tv-defaults.json` can bring some).
- **Home override**: Google TV's `launcherx` outranks any third-party HOME (it is privileged with a higher priority) even when the HOME role is ours. So with "Keep Dana TV as home" on, the key service catches Home (held: Android settings) and redirects whenever `launcherx`'s `.home.HomeActivity` comes forward (Back out of an app, boot).
- **TV audio stack quirks**: this TCL/MTK build can deadlock its whole audio stack. The mic's HAL input (`in_voc`, with MTK's hardware AEC plugin) stalls mid-read; an AudioFlinger dump then waits on the stream lock while holding AudioFlinger's lock, and every audio and `AudioService` binder call piles up (system-wide ANRs, eventually a system_server watchdog restart). The trigger found: AudioFlinger's `purgeStaleEffects_l` holding the input thread's lock while it tears down the effects (AEC/AGC/NS) of a record session whose app died, e.g. on every deploy. So on the TV `MicHub.effectsAllowed = false` (no effects on the mic session) and the echo-canceller setting is gone. Once it has locked up, only a reboot clears it, even with Dana TV stopped. Home Assistant's androidtv integration runs `dumpsys audio` every few seconds, which keeps poking it. **Never pipe `dumpsys media.audio_flinger` into `head`** (or anything that closes early): the audio HAL dies of SIGPIPE and audioserver restarts. Redirect to a file instead.
- **CameraPip**: a `TYPE_ACCESSIBILITY_OVERLAY` window (not focusable or touchable, so the remote still drives the app underneath) with Media3 ExoPlayer RTSP over TCP: low buffers, about 1–2 s latency. The player is **video only** (a custom `RenderersFactory` with just `MediaCodecVideoRenderer`, no audio renderer), **software decoded** (`c2.android.avc`) and lives on its own `dana-pip` thread. Each of these fixes a real failure. The TV's MTK hardware can't run a second video decoder: opening one tore down YouTube's 4K decoder and stalled its playback (it looked like "the network stops"). Building ExoPlayer's default audio sink calls into the audio policy service, and when the TV's audioserver is wedged that call never returns; on the main thread that was an ANR and a PiP stuck on "Connecting…". Software decoding costs about 20% of one core for the 30 fps front camera. Streams are go2rtc restreams on the LAN (e.g. `rtsp://frigate.local:8554/<camera>`), set per camera in the TV's settings.
- **Wake word / assistant**: the same `WakeWordService` as the kiosk (about ⅓ of one core on the TV). On a wake it starts the activity named in the service's `io.github.ronganam.dana.wake.ACTIVITY` meta-data, here the translucent `AssistantActivity`, its own task, which hosts `AssistantSession` + `FloatingAssistantOverlay` and goes to the back when the session closes. `DeviceSpeech` is off (`BuildConfig.TV`).
- **LanDns** (`DanaTvApplication`): a router with DNS rebind protection answers nothing for names that resolve to a LAN address, so OkHttp (`HttpClients.dns`) and the RTSP host lookup fall back to raw DNS queries against the build's `dana.lanDnsServers` (e.g. a Pi-hole), then 1.1.1.1.
- **TCL quirks**: updating an app unbinds its accessibility service and resets `accessibility_enabled` to 0. `KeyServiceGuard` repairs this on package-replaced, boot and every home resume: it rewrites `enabled_accessibility_services` without the service, waits 1 s, then writes it back with the service (back-to-back writes are coalesced and never bind). TCL's `TclAppBoot` blocks broadcast starts unless the `AUTO_START` app-op is allowed. `adb shell input keyevent` keys never reach an accessibility key filter; to test bindings, send real remote keys (the Android TV Remote protocol, e.g. the `androidtvremote2` Python library).
