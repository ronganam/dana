# Notifications: Inbox, direct push, alerts (phone flavor)

Server side: `server/docs/notifications.md`.

- **Direct push** (phone flavor; replaced the Home Assistant broadcasts): the server queues events in a numbered outbox and wakes the phone with a ping carrying only `seq` + `type` (server `docs/notifications.md`). **Transport** (`push/PushSetup`, phone source set): a build with your own Firebase project (`BuildConfig.FIREBASE_*` from `google-services.json`) uses **FCM** (`push/DanaMessagingService`, a high-priority data message); every other build — the released APKs, which have no Firebase config — uses **UnifiedPush** through a distributor app on the phone (`org.unifiedpush.android:connector`, `push/DanaUnifiedPushService`, both services not exported). The distributor is the one already chosen while it is installed, else ntfy (`io.heckel.ntfy`), else the first one installed (`Distributors.pick`); `UnifiedPush.register` asks it for an endpoint, `onNewEndpoint` sends it to the server (`POST /api/phone/register {transport: "unifiedpush", endpoint, app_version}`; FCM sends `{transport: "fcm", token}`; only the endpoint's host is logged), `onUnregistered` / `onRegistrationFailed` are kept as the problem Settings shows, and a message is the ping (`{"seq", "type"}` JSON, the same as FCM's data). Either service hands a ping to `push/PushPing` (shared, `main`): it notes the time (`push_last_ping_at`) and runs `push/PhoneEvents.catchUp` within 9 s (the FCM service blocks its worker thread for it; the UnifiedPush service, whose callbacks may run on the main thread, launches it on an IO scope). `catchUp` fetches `GET /api/phone/events?after=<push_last_seq>` with the app's token and dispatches each event: `alert` → `NotificationAlertReceiver.show`, `suggestions` → `SuggestionsReceiver.show`, `reminder` / `reminder_clear` → `ReminderReceiver.show` / `clear`, `notification_action` → `NotificationActionReceiver.handle`, `otp_request` → `MoneyCodes.handle` (below), `briefing` / `context_card` / `weekly_review` → `DanaCards` (see `docs/people.md`), `agent_sessions` → `AgentSessions` (below), `live` → `LiveActivities` (below), `notify` → a plain notification (channels `dana_messages`, `dana_important`, `dana_digest`; same tag replaces). Catch-up also runs on app start (`DanaApp` → `PushSetup.init`, main process only, which also registers: a fresh install starts at the server's `latest_seq`; a refusal — `fcm_not_configured` from a server without a Firebase key, `invalid_endpoint` — is kept as `push_problem` with the server's `detail`; getting an FCM token fails with `SERVICE_NOT_AVAILABLE` for ~15 s right after an install and Firebase doesn't retry, so FCM registration retries at 15 s / 1 m / 5 m / 15 m; the notification sync calls `PushSetup.ensureRegistered` again while unregistered for the build's transport or when the last registration is over 7 days old; an events response with `registered: false` (the server forgot the phone) triggers a new registration too) and on every `NotificationSyncWorker` run, so a lost ping only delays an event. Without a distributor installed nothing is registered and events wait for those checks. **Settings → Push** (phone only; `PushSetup.status` → `PushStatus`) shows the transport, the distributor app's name (UnifiedPush), whether the server has this phone, the last ping and the problem, if any; with no distributor it says "No distributor installed", explains installing ntfy (Google Play, else F-Droid; ntfy.sh by default or your own ntfy server) with a **Get ntfy** button, and coming back to Settings registers again. Firebase is initialised by hand from `BuildConfig.FIREBASE_*`, which Gradle reads from the site's or `app/src/phone/google-services.json` (no google-services plugin, so the kiosk/TV builds need no config; they get a no-op `PushSetup` from `src/nopush` and no Push section). The four "receivers" are now plain objects (names kept), so no other app can send them broadcasts. Tests: `PushPingTest` (a ping → its time, then one catch-up that fetches the events), `PushRegistrationTest` (the registration call per transport, refusals, the distributor pick).
- **Notification Inbox** (phone flavor only: declared in `src/phone/AndroidManifest.xml`): `DanaNotificationListener` (NotificationListenerService, needs "Notification access") extracts each notification (`NotificationExtractor`: MessagingStyle → last 5 messages with senders, InboxStyle lines, OTPs → `[code]` via `Redactor`), skips ongoing / foreground-service / progress / group summaries / Dana's own / denied apps (`NotificationSettings`: on/off, deny list, "skip banking & authenticator apps" on by default; with the `money` addon the bank / card apps go to money instead, below) and appends to the durable `NotificationOutbox` (`filesDir/notification_outbox.json`, write-then-rename, capped at 3000). Shade removals are queued with their reason. `NotificationSyncWorker` (WorkManager, unique `notification-sync`, 4 s debounce, network constraint, linear backoff; a run waiting out a retry backoff is REPLACEd so new notifications don't wait behind it). An hourly `notification-sync-hourly` periodic run is always scheduled (`ensurePeriodic`): besides reconciling, it keeps WorkManager from disabling its `RescheduleReceiver` each time the queue empties — every enable/disable is a `PACKAGE_CHANGED`, on which Android unbinds and re-binds the listener, and removals during that gap were lost (it used to loop every few seconds). Removals carry the raw Android `code`; children removed with reason 12 (group summary cancelled — swiping a whole group) take the summary's reason, and 24 (bundle dismissed) counts as a swipe. The "already sent" fingerprints are process-wide so a re-bind doesn't re-send the shade posts batches to `POST /api/notifications/batch`; items leave the outbox only after a 2xx, and the reply's `cancel_keys` (dismissed in Dana elsewhere) are cancelled in the shade (snoozed ones too: re-snoozed for 1 s, then cancelled — a listener can't cancel a snoozed key; the batch sends `snoozed_keys` for this). **Suggest-only**: the app never dismisses on its own. What the user sees of it is the Notifications place (below). **App icons** are real launcher icons: `AppIcons` saves each app's icon from the notification's own `android.appInfo` (no package-visibility workaround) to `filesDir/app_icons/` and the UI loads them from there (category emoji as fallback). They also go to the server so the web shows them (`AppIconSync`, `AppIconSyncWorker`, unique `app-icon-sync`, network constraint, 20 s debounce): requested after an icon is saved and when the listener connects; a run is due when the last one ended 6 h ago or more, or a saved package wasn't seen by it (`AppIconSyncPlan.due`; the last run's time and packages in `filesDir/app_icons_synced.txt`). It reads `GET /api/phone/app-icons` (package → the first 8 hex chars of the PNG's sha256), then `PUT /api/phone/app-icons/{package}` each icon as a 96 px PNG whose hash differs or is missing (`AppIconSyncPlan.toUpload`); a 400 / 413 skips that icon, 409 `too_many` stops, a 403 (phone addon not connected) forgets the addon (`Me.drop`) and waits 6 h, an unreachable server or 5xx waits quietly for the next request. Calls in `DevicesApi` (`appIcons`, `putAppIcon`); `AppIconSyncTest` pins the decisions against a fake server. App names come from the same `android.appInfo`. Settings → Notifications holds access, switches, per-app rules and the deny list. Calls and wire classes in `data/network/NotificationsApi.kt`. **Suggestion review**: tapping a suggestion (the pop-up, Now, the Debrief) opens `SuggestionEditSheet` with a `SuggestionSourceBlock` on top — app icon, app · sender · age, the notification text (or the call summary) with the evidence quote highlighted, and a link to the notification / call — and every field editable (reminder: title, due, remind-at, priority, group, and a full trigger editor — date / time pickers, place with zone + arrive/leave (zones from `GET /api/zones`, cached fallback), car enter/leave, wake — so triggers can be added, not just removed; event: title, start, end, place), then Create / Dismiss / Ask Dana. The Debrief uses the same sheet (now for events too).
- **Notifications place** (main screen): `NotificationOverviewController` reads `GET /api/notifications/overview` (polled every 20 s while on screen, plus sync on resume and `LiveRefresh` pings) and shows the noise box ("Clear the noise · N" → `POST /api/notifications/status {status: dismissed, bucket: dismiss}`; Clear all / Clear one use the same call with `package` / `ids`), "Dana noticed" rule suggestions (Keep it quiet / No), apps by count (icon, needs-you / interrupts flags, 2 summary points; the summary model's "[needs …]" flag is stripped by `summaryPoint` and shown as emphasis) and a "Quiet apps · N" fold. An app's page (stage unfolded, drill-down on the cover) loads `GET /api/notifications?package=` and has the three-way rule (`AppRule` → `POST /api/notifications/rules`: Interrupt me / Show here / Keep it quiet), the AI summary, and the waiting items with Reply (only while the shade still has a reply button; quick replies offered) / the app's own buttons (Mark as read, Archive … — the shade's non-text buttons, pressed in place via `PhoneNotificationActions.press`, so only while the notification is still in the shade) / Open / In 1 h / Clear, plus Clear all. Every change is optimistic (`OverviewMath`, tested); clearing cancels the returned `device_keys` in the shade and shows Undo for the `undo_id` (Undo restores in Dana only, the shade copy is gone). The page stays open, empty, after Clear all or a quieting rule. Rule changes have no `undo_id`; their Undo re-posts the old rule. Phone-only bits go through `PhoneNotificationActions` (live shade lookups).
- **Notification buttons** (7.10.0): `NotificationExtractor` sends each notification's buttons (`actions`: max 6 `{title, reply}`, `reply` = a free-form `RemoteInput`). An app's page in the Notifications place reads the live buttons from the shade (`DanaNotificationListener.liveActions` / `inShade`) and presses them in place (`perform(context, key, title, text)`: `RemoteInput.addResultsToIntent` for replies, BAL-allowed `ActivityOptions` on API 34+); Open uses the cached contentIntent, or the app's launcher intent once it left the shade. **From the web**: the server pushes a `notification_action` event with only `request_id`; `NotificationActionReceiver.handle` (dedupes repeats) fetches `GET /api/notifications/requests/{rid}` with the app's token, does it (`open` or a button title) and reports `POST .../requests/{rid}/result {ok, error}`. The text to send never travels in the push, so it never goes through Google.
- **Notification snooze**: `Snoozer` (15 min / 1 h / 3 h / This evening 20:00 before 19:00 / Tomorrow 08:00) from the alert screen. Server first (`POST /api/notifications/snooze`), then Android's own `snoozeNotification` for keys still in the shade; for ones no longer there, `SnoozeReturnWorker` (unique `snooze-return-<id>`) posts a "⏰ app" notification on channel `snoozed_notifications` when the time comes (tap → Inbox via `EXTRA_OPEN_INBOX`). Unsnooze / Undo clears the server and reposts the shade copy (re-snooze for 1 s — there is no public unsnooze). Snoozes from the web/agent arrive as `snooze_keys` in the batch reply.
- **Urgent notification alert**: the server's escalation pushes an `alert` event to `NotificationAlertReceiver.show` (phone flavor only). It ignores repeats of the same id + `attempt` within 10 min (the server re-nudges unseen ones with attempt 2, 3 → "still waiting" label) and opens `NotificationAlertActivity` directly when it may ("Display over other apps"), posting its notification quietly on `urgent_notifications_quiet` (no heads-up over the screen — the screen rings itself); otherwise (or if the start fails) it posts on channel `urgent_notifications` with a full-screen intent to `NotificationAlertActivity` (over the lock screen, turns the screen on, sound every 8 s + vibration for 60 s (strong full-amplitude buzz tagged as an alarm, so silent mode still vibrates)): Open in app (the cached contentIntent from `DanaNotificationListener.open`, else the launcher intent), snooze chips, Dismiss / Ask Dana / Got it (Open, Ask Dana and Got it call `POST /api/notifications/seen` so the re-nudges stop). In Do Not Disturb it only posts the notification. The detail view's "⚡ Alert me (full screen)" sets the `alert` rule for that app.
- **Suggestion pop-up**: the server's `suggestions` push event (fresh call / notification suggestions) reaches `SuggestionsReceiver.show` (phone flavor only). It posts a notification that stays until they're handled (channel `suggestion_review`, heads-up + full-screen intent; `suggestion_review_quiet` when the screen opens by itself) and, unless on a call (audio mode) or in DND, opens `SuggestionsPopupActivity` — needs "Display over other apps" (`SYSTEM_ALERT_WINDOW`; Settings → Pop-ups shows it and Android 14+'s full-screen-intent switch with buttons to the system pages). The screen shows the source once (`SuggestionSourceBlock`), a `SuggestionCard` per suggestion (Create / Edit sheet / Ask Dana / Dismiss) and Later; when none are pending (also when handled elsewhere) it shows "All handled", clears its notification and closes. The call result notification's Review opens it too. The notification is also dropped whenever its suggestions are all handled elsewhere (`SuggestionsReceiver.reconcile`, called after accept / dismiss and on every Inbox sync); dismissing a notification in Dana also cancels its urgent-alert notification. Names in mixed kicker lines are wrapped with `isolate()` (Unicode FSI/PDI) so Hebrew doesn't scramble "· 2h ago".

- **Coding-agent sessions** (`push/AgentSessions.kt`; server `docs/notifications.md` "Coding-agent sessions"): each `agent_sessions` push carries the whole list of the laptop's Claude Code / Codex sessions and `AgentSessions.plan` makes the shade match it (`agent_sessions_shown` in prefs remembers each id's last `rev`). Running / waiting → one ongoing notification per session (tag `agent_session:<id>`) asking to be promoted to a Live Update (`android.requestPromotedOngoing` extra, `POST_PROMOTED_NOTIFICATIONS`): title = the prompt's first line, text = the current activity + plan step, sub-text agent · project, a chronometer from the prompt, on API 36 `ProgressStyle` (one segment per plan step, indeterminate without a plan) and `setShortCriticalText` (the status-bar chip: "3/7", "Needs you" or the agent). Silent on `agent_sessions_live`; turning to waiting re-posts it once on `agent_sessions_alert`. Done / failed → the same tag becomes a normal alerting notification (once per `rev`, also when the phone never saw it running). Subagents (Claude Code's own, delegated child sessions) come inside their parent's entry (`subagents`), never as notifications of their own: without a plan, one `ProgressStyle` segment each (green done, blue running, orange waiting, red failed; finished ones fill the bar), "2/3 subagents done" in the text and the chip, their results listed in the finished notification; the server folds the group's status into the parent's, and a group shown live that stops being live is posted finished even on the same `rev`. A live one missing from the list is cancelled; each also times out after an hour without an update. Tapping it (live or finished) opens the session's `open_url` (https only, whatever the server's hook sent) as a plain `ACTION_VIEW` + `CATEGORY_BROWSABLE` intent — no app is named, so Android picks the app that verified that link's domain, else the browser; without one, Dana. **Hide** (`AgentSessionReceiver`) cancels it and calls `DELETE /api/agent-sessions/{id}`. The receiver and the permission are declared only in the phone manifest.

- **Live activities** (`push/LiveActivities.kt`, models `data/models/LiveModels.kt`, calls `data/network/LiveApi.kt` = `api.live`; server `core/live.py`, contract fixture `server/tests/fixtures/live_web.json`): one generic renderer for whatever an add-on keeps live (a watched train, a timer); add-ons describe it in plain fields and never touch Android's. Each `live` push carries every activity (`{"activities": [...]}`, the same object as `GET /api/live`) and `LiveActivities.plan` makes the shade match it: shown state per id in prefs (`live_shown`: `{rev, alert, live}`); a running one is (re-)posted as an ongoing notification (tag `live:<id>`, id 1) asking to be promoted to a Live Update (`android.requestPromotedOngoing`, `POST_PROMOTED_NOTIFICATIONS`; never colorized, no custom views), silent on `live_<addon>` "<source> · live" (default importance, no sound / vibration / badge) or, when its `alert` is non-empty and not the last one shown for that id, once on `live_<addon>_alert` "<source> · alerts" (high); both channels are created on first use in the channel group "Live". An ended one with a `final` is posted once per `rev` as a normal auto-cancelling notification on the alert channel and then forgotten; an ended one without a final, or a shown one missing from the list, is cancelled. What it shows is the activity's fields overridden by its selected choice's (`LiveActivity.look`; `selected` "" or unknown = the first choice): small icon = the `icon` (`ic_live_<name>`, the server's ICONS as Lucide outlines; unknown → Dana's), accent = the tone (neutral #5B8DEF, good #3DB86B, warn #FF9F1A, bad #E5484D, muted #8A8F98), title / text / sub-text (`context`, else the source), category progress (reminder when alerting or tone bad); `countdown` → a chronometer counting down to it, `since` → one counting up, neither → no time; `chip` → `setShortCriticalText` (the status-bar chip, API 36); `progress` → `Notification.ProgressStyle` on API 36 (segments and points in tone colours, `value`, the `tracker` icon riding the bar, indeterminate, `styled_by_progress`), a plain progress bar before; `ends_at` → `setTimeoutAfter` (already past: cancelled). Tapping it opens `open`: https → `ACTION_VIEW` + `CATEGORY_BROWSABLE` (the app that verified the domain, else the browser); "/path" → that screen of the app when its first segment is one `ShellController.openRoute` knows (`/money/plan` → Money), else Dana's web app at that path (an add-on's panel, e.g. `/israel_rail`); empty → Dana. Buttons (≤ 3) go to `LiveActivityReceiver` (phone manifest, not exported): `next` / `prev` switch the choice at once from the cached payload (`filesDir/live_activities.json`, the last list drawn) and then `POST /api/live/{id}/select`; while the server can't be reached the choice waits in `live_pending_select` (it wins over the pushed `selected` and is sent again after each `live` push); `next` is hidden on the last choice, `prev` on the first. A `server` action → `POST /api/live/{id}/act`, redrawn from the reply (`activity: null` = ended → cancelled). `stop`, and swiping it away (the delete intent), cancel it and `DELETE /api/live/{id}`. Tests: `LiveActivitiesTest` (plan, the merge, next/prev bounds and hiding, tap targets, every server icon has a drawable, the fixture parsed leniently and round-tripped through the cache).

- **Money: bank sign-in codes and bank / card notifications** (`data/money/`; the server's `money` addon). *Sign-in codes*: when the server signs in to a bank that texts a code, it pushes `otp_request` with only `request_id`. `MoneyCodes.handle` fetches `GET /api/money/code-requests/{id}`; while it is `pending` it **arms** it (senders, `code_regex`, `expires_at` capped at 10 min, in `filesDir/money_code_requests.json` so it survives the process dying; several may be armed, expired ones are dropped; a regex that doesn't compile on the JVM is never armed) and checks the shade at once (the SMS may be there already; again when the listener reconnects). `DanaNotificationListener.onNotificationPosted` calls `MoneyCodes.onPosted` first, before capture, redaction, skipping and the "Send notifications to Dana" switch; with nothing armed it reads nothing. A notification matches when its sender (the title, or a MessagingStyle message's sender; case-insensitive, trimmed, direction marks dropped) is one of `senders` and its text (text / big text / the MessagingStyle messages) matches `code_regex` (group 1, else the match's digits); the newest matching message wins, and messages from over 2 min before the arming (an earlier sign-in's SMS still in the shade) or whose code was already handed over are ignored. The code goes only to `POST /api/money/code-requests/{id}` `{code}`: 200 / 400 `bad_code` / 404 / 409 `not_pending` disarm, unreachable or 5xx retries with backoff until expiry. It is never logged, stored or shown; the Inbox copy of the SMS is still `[code]`. Pure matching in `MoneyCodes` (`MoneyCodesTest`). *Signals*: Cal, Hapoalim, Max and Isracard (`MoneySignals.PACKAGES`). While `/api/me` lists `money` (`Me`, cached in prefs, re-read on every app start / foreground) and "Send notifications to Dana" is on, their notifications (title + text through `Redactor`) go to `filesDir/money_signals.json` and `NotificationSyncWorker` drains it to `POST /api/money/signals` in the same debounced, retried runs; they never reach `/api/notifications/batch` (removals neither), whatever "skip banking & authenticator apps" says: that switch governs the Inbox only. A 403 `not_connected` drops the addon from the cache and the queue until the next `/api/me`. Without `money` these apps behave as before.
