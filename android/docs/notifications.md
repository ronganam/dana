# Notifications: Inbox, direct push, alerts (phone flavor)

Server side: the server repo's `docs/notifications.md`.

- **Direct push** (7.11.0, phone flavor; replaced the Home Assistant broadcasts): the server queues events in a numbered outbox and wakes the phone with a high-priority FCM data message carrying only `seq` + `type` (`push/DanaMessagingService`, phone source set, not exported). `push/PhoneEvents.catchUp` then fetches `GET /api/phone/events?after=<push_last_seq>` with the app's token and dispatches each event: `alert` → `NotificationAlertReceiver.show`, `suggestions` → `SuggestionsReceiver.show`, `reminder` / `reminder_clear` → `ReminderReceiver.show` / `clear`, `notification_action` → `NotificationActionReceiver.handle`, `otp_request` → `MoneyCodes.handle` (below), `briefing` / `context_card` / `weekly_review` → `DanaCards` (see `docs/people.md`), `agent_sessions` → `AgentSessions` (below), `notify` → a plain notification (channels `dana_messages`, `dana_important`, `dana_digest`; same tag replaces). Catch-up also runs on app start (`DanaApp` → `PushSetup.init`, main process only, which also registers the token: `POST /api/phone/register`, `push_device_id` UUID; a fresh install starts at the server's `latest_seq`; getting the token fails with `SERVICE_NOT_AVAILABLE` for ~15 s right after an install and Firebase doesn't retry, so `PushSetup.ensureRegistered` retries at 15 s / 1 m / 5 m / 15 m, and the notification sync calls it again while unregistered or when the last registration is over 7 days old; an events response with `registered: false` (the server forgot the phone) triggers a new registration too) and on every `NotificationSyncWorker` run, so a lost ping only delays an event. Firebase is initialised by hand from `BuildConfig.FIREBASE_*`, which Gradle reads from `app/src/phone/google-services.json` (no google-services plugin, so the kiosk/TV builds need no config; they get a no-op `PushSetup` from `src/nopush`). The four "receivers" are now plain objects (names kept), so no other app can send them broadcasts.
- **Notification Inbox** (phone flavor only: declared in `src/phone/AndroidManifest.xml`): `DanaNotificationListener` (NotificationListenerService, needs "Notification access") extracts each notification (`NotificationExtractor`: MessagingStyle → last 5 messages with senders, InboxStyle lines, OTPs → `[code]` via `Redactor`), skips ongoing / foreground-service / progress / group summaries / Dana's own / denied apps (`NotificationSettings`: on/off, deny list, "skip banking & authenticator apps" on by default; with the `money` integration the bank / card apps go to money instead, below) and appends to the durable `NotificationOutbox` (`filesDir/notification_outbox.json`, write-then-rename, capped at 3000). Shade removals are queued with their reason. `NotificationSyncWorker` (WorkManager, unique `notification-sync`, 4 s debounce, network constraint, linear backoff; a run waiting out a retry backoff is REPLACEd so new notifications don't wait behind it). An hourly `notification-sync-hourly` periodic run is always scheduled (`ensurePeriodic`): besides reconciling, it keeps WorkManager from disabling its `RescheduleReceiver` each time the queue empties — every enable/disable is a `PACKAGE_CHANGED`, on which Android unbinds and re-binds the listener, and removals during that gap were lost (it used to loop every few seconds). Removals carry the raw Android `code`; children removed with reason 12 (group summary cancelled — swiping a whole group) take the summary's reason, and 24 (bundle dismissed) counts as a swipe. The "already sent" fingerprints are process-wide so a re-bind doesn't re-send the shade posts batches to `POST /api/notifications/batch`; items leave the outbox only after a 2xx, and the reply's `cancel_keys` (dismissed in Dana elsewhere) are cancelled in the shade (snoozed ones too: re-snoozed for 1 s, then cancelled — a listener can't cancel a snoozed key; the batch sends `snoozed_keys` for this). **Suggest-only**: the app never dismisses on its own. What the user sees of it is the Notifications place (below). **App icons** are real launcher icons: `AppIcons` saves each app's icon from the notification's own `android.appInfo` (no package-visibility workaround) to `filesDir/app_icons/` and the UI loads them from there (category emoji as fallback). App names come from the same `android.appInfo`. Settings → Notifications holds access, switches, per-app rules and the deny list. JSON in `data/network/NotificationJson.kt`. **Suggestion review**: tapping a suggestion (the pop-up, Now, the Debrief) opens `SuggestionEditSheet` with a `SuggestionSourceBlock` on top — app icon, app · sender · age, the notification text (or the call summary) with the evidence quote highlighted, and a link to the notification / call — and every field editable (reminder: title, due, remind-at, priority, group, and a full trigger editor — date / time pickers, place with zone + arrive/leave (zones from `GET /api/zones`, cached fallback), car enter/leave, wake — so triggers can be added, not just removed; event: title, start, end, place), then Create / Dismiss / Ask Dana. The Debrief uses the same sheet (now for events too).
- **Notifications place** (main screen): `NotificationOverviewController` reads `GET /api/notifications/overview` (polled every 20 s while on screen, plus sync on resume and `LiveRefresh` pings) and shows the noise box ("Clear the noise · N" → `POST /api/notifications/status {status: dismissed, bucket: dismiss}`; Clear all / Clear one use the same call with `package` / `ids`), "Dana noticed" rule suggestions (Keep it quiet / No), apps by count (icon, needs-you / interrupts flags, 2 summary points; the summary model's "[needs …]" flag is stripped by `summaryPoint` and shown as emphasis) and a "Quiet apps · N" fold. An app's page (stage unfolded, drill-down on the cover) loads `GET /api/notifications?package=` and has the three-way rule (`AppRule` → `POST /api/notifications/rules`: Interrupt me / Show here / Keep it quiet), the AI summary, and the waiting items with Reply (only while the shade still has a reply button; quick replies offered) / the app's own buttons (Mark as read, Archive … — the shade's non-text buttons, pressed in place via `PhoneNotificationActions.press`, so only while the notification is still in the shade) / Open / In 1 h / Clear, plus Clear all. Every change is optimistic (`OverviewMath`, tested); clearing cancels the returned `device_keys` in the shade and shows Undo for the `undo_id` (Undo restores in Dana only, the shade copy is gone). The page stays open, empty, after Clear all or a quieting rule. Rule changes have no `undo_id`; their Undo re-posts the old rule. Phone-only bits go through `PhoneNotificationActions` (live shade lookups).
- **Notification buttons** (7.10.0): `NotificationExtractor` sends each notification's buttons (`actions`: max 6 `{title, reply}`, `reply` = a free-form `RemoteInput`). An app's page in the Notifications place reads the live buttons from the shade (`DanaNotificationListener.liveActions` / `inShade`) and presses them in place (`perform(context, key, title, text)`: `RemoteInput.addResultsToIntent` for replies, BAL-allowed `ActivityOptions` on API 34+); Open uses the cached contentIntent, or the app's launcher intent once it left the shade. **From the web**: the server pushes a `notification_action` event with only `request_id`; `NotificationActionReceiver.handle` (dedupes repeats) fetches `GET /api/notifications/requests/{rid}` with the app's token, does it (`open` or a button title) and reports `POST .../requests/{rid}/result {ok, error}`. The text to send never travels in the push, so it never goes through Google.
- **Notification snooze**: `Snoozer` (15 min / 1 h / 3 h / This evening 20:00 before 19:00 / Tomorrow 08:00) from the alert screen. Server first (`POST /api/notifications/snooze`), then Android's own `snoozeNotification` for keys still in the shade; for ones no longer there, `SnoozeReturnWorker` (unique `snooze-return-<id>`) posts a "⏰ app" notification on channel `snoozed_notifications` when the time comes (tap → Inbox via `EXTRA_OPEN_INBOX`). Unsnooze / Undo clears the server and reposts the shade copy (re-snooze for 1 s — there is no public unsnooze). Snoozes from the web/agent arrive as `snooze_keys` in the batch reply.
- **Urgent notification alert**: the server's escalation pushes an `alert` event to `NotificationAlertReceiver.show` (phone flavor only). It ignores repeats of the same id + `attempt` within 10 min (the server re-nudges unseen ones with attempt 2, 3 → "still waiting" label) and opens `NotificationAlertActivity` directly when it may ("Display over other apps"), posting its notification quietly on `urgent_notifications_quiet` (no heads-up over the screen — the screen rings itself); otherwise (or if the start fails) it posts on channel `urgent_notifications` with a full-screen intent to `NotificationAlertActivity` (over the lock screen, turns the screen on, sound every 8 s + vibration for 60 s (strong full-amplitude buzz tagged as an alarm, so silent mode still vibrates)): Open in app (the cached contentIntent from `DanaNotificationListener.open`, else the launcher intent), snooze chips, Dismiss / Ask Dana / Got it (Open, Ask Dana and Got it call `POST /api/notifications/seen` so the re-nudges stop). In Do Not Disturb it only posts the notification. The detail view's "⚡ Alert me (full screen)" sets the `alert` rule for that app.
- **Suggestion pop-up**: the server's `suggestions` push event (fresh call / notification suggestions) reaches `SuggestionsReceiver.show` (phone flavor only). It posts a notification that stays until they're handled (channel `suggestion_review`, heads-up + full-screen intent; `suggestion_review_quiet` when the screen opens by itself) and, unless on a call (audio mode) or in DND, opens `SuggestionsPopupActivity` — needs "Display over other apps" (`SYSTEM_ALERT_WINDOW`; Settings → Pop-ups shows it and Android 14+'s full-screen-intent switch with buttons to the system pages). The screen shows the source once (`SuggestionSourceBlock`), a `SuggestionCard` per suggestion (Create / Edit sheet / Ask Dana / Dismiss) and Later; when none are pending (also when handled elsewhere) it shows "All handled", clears its notification and closes. The call result notification's Review opens it too. The notification is also dropped whenever its suggestions are all handled elsewhere (`SuggestionsReceiver.reconcile`, called after accept / dismiss and on every Inbox sync); dismissing a notification in Dana also cancels its urgent-alert notification. Names in mixed kicker lines are wrapped with `isolate()` (Unicode FSI/PDI) so Hebrew doesn't scramble "· 2h ago".

- **Coding-agent sessions** (`push/AgentSessions.kt`; server `docs/notifications.md` "Coding-agent sessions"): each `agent_sessions` push carries the whole list of the laptop's Claude Code / Codex sessions and `AgentSessions.plan` makes the shade match it (`agent_sessions_shown` in prefs remembers each id's last `rev`). Running / waiting → one ongoing notification per session (tag `agent_session:<id>`) asking to be promoted to a Live Update (`android.requestPromotedOngoing` extra, `POST_PROMOTED_NOTIFICATIONS`): title = the prompt's first line, text = the current activity + plan step, sub-text agent · project, a chronometer from the prompt, on API 36 `ProgressStyle` (one segment per plan step, indeterminate without a plan) and `setShortCriticalText` (the status-bar chip: "3/7", "Needs you" or the agent). Silent on `agent_sessions_live`; turning to waiting re-posts it once on `agent_sessions_alert`. Done / failed → the same tag becomes a normal alerting notification (once per `rev`, also when the phone never saw it running). Subagents (Claude Code's own, T3 Code delegated children) come inside their parent's entry (`subagents`), never as notifications of their own: without a plan, one `ProgressStyle` segment each (green done, blue running, orange waiting, red failed; finished ones fill the bar), "2/3 subagents done" in the text and the chip, their results listed in the finished notification; the server folds the group's status into the parent's, and a group shown live that stops being live is posted finished even on the same `rev`. A live one missing from the list is cancelled; each also times out after an hour without an update. Tapping it (live or finished) opens the session's `open_url` (its T3 Code thread, `https://app.t3.codes/threads/…`), aimed at the T3 Code app (`com.t3tools.t3code`, listed in `<queries>`) when installed, else the browser; without one, Dana. **Hide** (`AgentSessionReceiver`) cancels it and calls `DELETE /api/agent-sessions/{id}`. Kiosk / TV remove the receiver and the permission.

- **Money: bank sign-in codes and bank / card notifications** (`data/money/`; the server's `money` kind). *Sign-in codes*: when the server signs in to a bank that texts a code, it pushes `otp_request` with only `request_id`. `MoneyCodes.handle` fetches `GET /api/money/code-requests/{id}`; while it is `pending` it **arms** it (senders, `code_regex`, `expires_at` capped at 10 min, in `filesDir/money_code_requests.json` so it survives the process dying; several may be armed, expired ones are dropped; a regex that doesn't compile on the JVM is never armed) and checks the shade at once (the SMS may be there already; again when the listener reconnects). `DanaNotificationListener.onNotificationPosted` calls `MoneyCodes.onPosted` first, before capture, redaction, skipping and the "Send notifications to Dana" switch; with nothing armed it reads nothing. A notification matches when its sender (the title, or a MessagingStyle message's sender; case-insensitive, trimmed, direction marks dropped) is one of `senders` and its text (text / big text / the MessagingStyle messages) matches `code_regex` (group 1, else the match's digits); the newest matching message wins, and messages from over 2 min before the arming (an earlier sign-in's SMS still in the shade) or whose code was already handed over are ignored. The code goes only to `POST /api/money/code-requests/{id}` `{code}`: 200 / 400 `bad_code` / 404 / 409 `not_pending` disarm, unreachable or 5xx retries with backoff until expiry. It is never logged, stored or shown; the Inbox copy of the SMS is still `[code]`. Pure matching in `MoneyCodes` (`MoneyCodesTest`). *Signals*: Cal, Hapoalim, Max and Isracard (`MoneySignals.PACKAGES`). While `/api/me` lists `money` (`Me`, cached in prefs, re-read on every app start / foreground) and "Send notifications to Dana" is on, their notifications (title + text through `Redactor`) go to `filesDir/money_signals.json` and `NotificationSyncWorker` drains it to `POST /api/money/signals` in the same debounced, retried runs; they never reach `/api/notifications/batch` (removals neither), whatever "skip banking & authenticator apps" says: that switch governs the Inbox only. A 403 `not_connected` drops the kind from the cache and the queue until the next `/api/me`. Without `money` these apps behave as before.
