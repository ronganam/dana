# Wear OS watch (`:wear`)

## Pairing

The watch is its own device of the user (listed and revocable on the web Devices page, server `docs/devices.md`) with its own token; nothing travels from the phone but a one-time code. Today the watch uses the token for nothing else (its requests go through the phone), so revoking it on the Devices page only removes it from the list.

- **Through the phone** (`data/WatchPairing.kt`): when the watch app starts, and when the phone's config (`/dana_config`, which carries the phone's server but no token) names a server the watch isn't paired with, the watch sends `/pair_watch` `WearPairRequest{name: <model>}`. The phone (`WatchPairingOffer`) starts a pairing of kind `watch` with its own token (`POST /api/devices/pairings`) and answers on `/response/pair_watch` with `WearPairOffer{server, code}` or `{error}` (the phone isn't paired, the server refused). The watch redeems the code itself: `POST /api/pair {code, kind: "watch", name}` (`WatchPairClient`, plain `HttpURLConnection`), and keeps the server, token, device id and name in `DanaWearPrefs`.
- **Without the phone**: no phone node → the pairing screen (`ui/screens/PairScreen.kt`, route `pair`) opens by itself once per process, with the code entry (server address + code from the Devices page → Pair a device → Watch) and "Ask the phone". No answer from the phone in 20 s, or a refusal, shows the same screen's message; Settings → "Dana account" opens it any time and shows "Paired as …".
- `WatchPairingFlow` holds the steps without Android (phone link, offer, redeem, save) and is unit-tested with fakes; `WatchPairClient` is tested against a local HTTP server (`wear/src/test/.../data/WatchPairingTest.kt`); the messages in `protocol/src/test/.../PairingTest.kt`.
- **What needs real devices**: emulators can't do the phone ↔ watch round trip (the Data Layer needs the Play Store Wear OS app), so `/pair_watch` end to end, the automatic re-pair when the phone's server changes, and the watch reaching the server over the phone's connection are checked on hardware only. A release watch app reaches only HTTPS servers.

## Watch assistant performance (`:wear`)

Built and measured on a OnePlus Watch 2 (OPWE242, Wear OS 4, 32-bit arm); an emulator is often attached too, so always pass `-s`. Its button opens Dana with a plain launcher intent (Google Assistant stays the system assistant), so a press goes MAIN → `MainActivity` → `WearViewModel.onAppOpened` → hands-free listening. `WearVoiceInteractionService` covers the case where Dana is made the default assistant.

- **Timing**: `adb -s <watch> logcat -s DanaPerf` (`wear/perf/WearPerf.kt`, same tag as `OpenTimer`) logs each turn: activity created, phone node, mic opened, listening shown (first frame with the listening state), first audio frame, first audio sent, speech heard, end of speech / stop, transcript shown, first reply text shown, reply text shown, plus a `voice turn levels:` line (RMS percentiles vs the 700 threshold) to tune from. Measured on the watch from the system's activity start to the mic recording (audio policy `MSG_RECORD_START`): before 1.1–1.3 s (and every press while a stuck turn ran did nothing); after 0.16–0.24 s, with the listening screen's first frame at 0.35–0.5 s (before 0.5–0.7 s). The measuring script: launch with `am start -W` 130 s apart (the 2-minute "mid-conversation" window), then read `START u0`, `Displayed` and `MSG_RECORD_START` from `logcat -v monotonic`.
- **Mic first**: `MainActivity.onCreate` gets the ViewModel itself and starts the turn **before** `setContent`. The mic runs on its own urgent-audio thread (`dana-mic`) at once; audio is buffered in a channel until the phone's node id is known (`PhoneNode`, cached per process and prefetched), then sent in order as 100 ms `/voice_chunk` messages, followed by `/voice_stop` or `/voice_cancel` from the same sender. Never put a Play Services round trip, a network call or composition in front of `AudioRecord.startRecording()`.
- **Hands-free turns** (app open / assist): a haptic tick at the press; cancelled after 8 s without speech; sent after 1.5 s of quiet following speech (5 loud 20 ms frames in a row; the first 800 ms never count: every turn on the OnePlus starts with a burst of RMS 1200–3200 about 340–640 ms after the first frame, tick or not, and it alone used to count as speech). A mic tap starts a turn that runs until Stop. Leaving the app (`onStop`) sends a turn that heard speech and drops one that didn't. Before this, one loud blip kept a hands-free turn recording silence in the background for 90 s, and every press in that time did nothing.
- **Idle screen** (`ui/screens/TodayBlock.kt`, the website's "06:52" scene): while nothing has been said, the main screen shows, above the mic, the greeting in mono caps (ember text, by the hour), the paired user's first name in Instrument Serif (`WearPrefs.userName`, from the pairing's answer; the weekday before a pairing that said) and up to three dot lines from the phone's snapshot: the next events (sky), "N need you" from the Inbox (teal), due tasks (amber, overdue ember). Pure rules in `WatchToday` (`WatchTodayTest`). Tiles stay as they are (ProtoLayout has only the system fonts).
- **Thread**: every watch turn goes to Dana's shared thread (`session_id: "main"`, `device: "watch"`, server `docs/agent-actions.md`). There is no session list or new session: the side menu has "Latest in the thread" (the last 12 turns, each cut to 280 characters, from `get_session_detail`) and "Clear the screen" (local only). The phone bridge answers the old `get_sessions` / `create_session` paths with the thread, and a busy thread (409 `session_busy`) comes back as a calm line instead of an error.
- **Phone bridge** (`WearMessageListenerService` on the phone; every path and every payload live in the `:protocol` module, used by both `:app` and `:wear`: `WearPaths`, `WearPayloads.kt` (config, version, reminders, task actions), `WearData.kt` (the snapshot `DanaSnapshot`, cards, suggestion actions, shopping requests / answers, the watch's task and event lists) and `WearAssistant.kt` (`WearSendMessage`, `WearRunAction`, the reply frames `WearReply`). They are `@Serializable` classes read with `WearJson` (unknown keys ignored, a missing field takes its default; `decode` returns null when a required field is missing or the text doesn't read); a new path or payload goes there, and a manifest `pathPrefix` filter in `wear/src/main/AndroidManifest.xml` must match it): `/voice_*` frames are handled on the listener thread in arrival order (launching each on the IO pool could reorder chunks or drop the ones before the socket existed). It forwards `{"transcription"}` as soon as the server sends it and `{"partial_response"}` (reply text so far, at most every 400 ms) before the folded final reply; the watch shows them as the user bubble and a growing reply bubble.
- **Release builds**: R8 (`wear/proguard-rules.pro`, no obfuscation) plus `wear/src/main/baseline-prof.txt`. `bin/deploy-app.sh --watch-ip <ip:port | adb serial>` force-installs the profile and runs `cmd package compile -m speed-profile -f` after installing. Install the **release** APK on the watch (`adb -s <watch> install -r wear/build/outputs/apk/release/wear-release.apk`): it carries the release key that matches the phone; the debug APK has a different signature and would need an uninstall (which wipes the watch's settings).

## Other watch notes

- **Watch scrolling**: use `Modifier.rotaryScroll(state, focusRequester, active)` (`wear/ui/components/Rotary.kt`) on every scrollable list. Compose sends rotary events to the focused node and its *ancestors*, so the handler must come **before** `focusable()`. The old screens had it after, and the crown did nothing. Pages of a `HorizontalPager` pass `active = currentPage == page`, or the last composed page keeps the focus. All watch UIs sit inside `DanaWearTheme` (the phone's dark Ink & Paper palette, Instrument Serif / DM Mono bundled in `wear/res/font`).
- **Watch alarm**: `WearReminderActivity` has round Snooze / Done / Dismiss actions. Turning the crown, or tapping Snooze, opens a picker that steps through the same choices as the phone's dial (time, wake, car, each zone arrive/leave), with a gauge of dots around the edge. The phone sends its Home Assistant zones with each alarm (`zones` in `/wear/reminder_alarm`, cached in `zones_cache`), and `/snooze_task` passes through `type` + `minutes|location+event|action`.
- Wear app: opening it starts listening on a clear screen (same thread), unless a turn is in progress (recording, waiting for a reply, a pending prompt, or activity in the last 2 minutes). Hands-free listening cancels itself after 8 s without speech and sends after 1.5 s of quiet following speech (see "Watch assistant performance"). The old per-watch conversation id (`watch_session_id`) is gone.

## Dana cards, tiles, complications (7.15)

- `cards/DanaCardListenerService` (path prefix `/wear/dana_`) handles three paths:
  - `/wear/dana_card {kind, title, subtitle, lines[], ref}` posts one notification per kind (`caller`, `meeting`, `briefing`).
  - `/wear/dana_card_clear {kind}` removes it.
  - `/wear/dana_snapshot` stores the phone's trimmed widget snapshot (`DanaSnapshot.forWatch()`, kept by `SnapshotStore` in `cards/DanaCards.kt`).
- Tiles (`tiles/DanaTiles.kt`, `tiles/ShoppingTileService.kt`):
  - **Today** shows the briefing headline (today's only), the next events and the top due tasks.
  - **Waiting on you** shows the pending count plus the newest suggestion with Accept / Dismiss. The buttons go through `SuggestionActionActivity`, which sends `/suggestion_action {id, action}` to the phone; the phone calls the server and sends a fresh snapshot.
  - **Shopping** shows "SHOPPING · N", the first four items to buy (with quantity) and "+N more"; a tap opens the Shopping screen.
- Complications (`SHORT_TEXT`, refreshed when a snapshot arrives): Inbox needs-you count (opens Dana), shopping items left (`shopping_count` with the watch's own waiting ticks applied; opens the Shopping screen).
- The phone's side lives in `docs/people.md`.

## Shopping (`wear/.../shopping/`)

Ticking things off in the supermarket with the phone in a pocket. Opened from the Shopping complication, the Shopping tile, the side menu ("Shopping") and its own launcher entry ("Shopping", `ShoppingActivity`).

| File | What |
|---|---|
| `ShopModel.kt` | Pure rules (`Shop`, tested by `wear/src/test/.../ShopModelTest.kt`): the snapshot's shopping part (`ShopList.parse`), rows with aisle labels, ticks / unticks / Undo, the request queue, answers, timeouts, a new snapshot over requests on their way, the queue's JSON, direction by script |
| `WatchShopping.kt` | The process's state (`StateFlow<ShopState>`), sending one request at a time, the answer listener, timers, the queue in `DanaWearPrefs` (`shopping_pending`) |
| `ShoppingLink.kt` | `/shopping_action` to the phone over the data layer (`PhoneNode`) |
| `ShoppingActivity.kt` / `ShoppingScreen.kt` | The screen and the speech input for Add |
| `src/debug/.../DebugPhone.kt` (+ a no-op twin in `src/release`) | Debug builds only: a stand-in phone for an unpaired watch (below) |

- **The screen**: a serif "Shopping" title with the count in mono ("7 TO BUY", "VIEW ONLY · 7 TO BUY"; nothing when the list is empty), Add, then the items in the snapshot's order with a quiet mono label where the aisle changes. Each row is a 52 dp pill: a ring, the name (16 sp, two lines) and the quantity under it. Rows are one column: every name starts next to the ring whatever its language, and each text runs in its own direction (`Shop.mostlyRtl`). `ScalingLazyColumn` + `rotaryScroll` (the crown).
- **A tap** ticks: a `CONFIRM` haptic, the row turns ticked at once, stays `LINGER_MS` (1 s; a second tap puts it back) and leaves. Undo is offered for 5 s after it leaves, as a pill at the **top** edge (at the bottom it covered the next row while ticking down the list, so a quick second tap put the first item back). Undo sends `uncheck` (or drops a tick still waiting on the watch) and the row comes back where it was.
- **Empty**: "Nothing to buy." + "Add by voice, or tell Dana."; everything ticked during this visit: "All done." + "N ticked off" (a visit starts at `onStart`). A read-only list (`shopping_can_edit` false): "VIEW ONLY", rows without rings and not tappable, no Add. No snapshot yet: "No list yet. Open Dana on your phone."
- **Add by voice**: `RecognizerIntent.ACTION_RECOGNIZE_SPEECH` (the manifest's `<queries>` makes it visible); the button is absent when nothing on the watch answers it. The text goes as `add`; the phone splits it like its add field. The line under the title says "Added: milk, eggs", or the phone's `error` sentence.
- **To the phone**: `/shopping_action {action: check | uncheck, id, list_id, ref}` or `{action: add, text, list_id, ref}`, one at a time in order. The phone answers on `/response/shopping_action {ok, queued, error?, ref}` (`ref` comes back as sent; `queued: true` is done). A refusal drops the request, the row comes back and the `error` sentence shows. A request the phone took but never answered counts as done after 8 s.
- **Phone not reachable**: the tick is **kept on the watch** (shown done, saved in `shopping_pending`, so it survives the app stopping) and the screen says "Phone not reachable · N waiting". Waiting requests go out, in order, when a snapshot arrives (the phone is there), the screen opens, the next tick is made, or every 10 s while the screen shows. A request sent before the app stopped is taken as answered on the next start (the phone has it). An add made while unreachable says "Phone not reachable. Will add “…” when it's back."
- **A new snapshot** replaces the list without undoing a tick in flight: requests the phone answered leave the queue (the snapshot, sent 1.5 s after the change, already has them), requests still on their way stay applied on top, and rows are keyed by item id so nothing jumps more than the change itself. `SnapshotStore.save` hands every snapshot to `WatchShopping.onSnapshot`; a local change that alters the count refreshes the tile and the complication.
- **Debug fake phone** (emulators can't pair without the Play Store Wear OS app on the phone): `adb -s <watch> shell am broadcast -n io.github.ronganam.dana/io.github.ronganam.dana.wear.shopping.DebugShoppingReceiver --es phone ok|unreachable|refuse|off --es snapshot_b64 <base64 JSON> --es say_b64 <base64 text>`. `ok` answers like the phone and sends a snapshot with the change 1.5 s later; `unreachable` refuses every send; `refuse` answers "This list is view only."; `snapshot_b64` stores a snapshot as if the phone sent it; `say_b64` adds text as if spoken. Not in release builds (the receiver lives in `src/debug`).
- Tests: `./gradlew :wear:testDebugUnitTest` (JUnit, the same version as `:app`); the payloads themselves: `./gradlew :protocol:testDebugUnitTest`.
