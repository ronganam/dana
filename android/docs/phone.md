# Phone app features

## Pairing

The phone has no server or token built in: it pairs with a Dana server once and then talks to it with its own device token (server `docs/devices.md`).

- **First run / unpaired**: `MainActivity` shows `ui/screens/PairingScreen` instead of the shell while `MainViewModel.paired` is false (and while `PairingController.state.requested`: Settings → "Pair again", or a link opened while paired). The screen says to open the web Devices page → Pair a device → Phone and scan its QR code with the camera, and has the same thing as a form: server address + the 8-character code (`K7QM 4XPZ`; case, spaces and dashes don't matter).
- **The QR link**: the Devices page's QR code holds `dana://pair?server=<base URL>&code=<code>`. The phone flavor's `MainActivity` has an intent filter for `dana://pair` (VIEW, BROWSABLE), so a camera app that opens links opens Dana with it (no scanner library in the app). An unpaired phone pairs at once; a paired one shows the form filled in, and pairing replaces the old pairing.
- **The call**: `PairingController` (in `ui/viewmodels/`) is the phone's layer over the shared `data/pairing/PairingFlow` (the form, the servers found on this network as chips, the code check) with `PairingClient.pair(server, code, "phone", DevicePairing.deviceName())` = `POST /api/pair` without a token. `DevicePairing.store` keeps the token in `ServerConfig` and the device (name, user) beside it, `MainViewModel.useServerConfig` points the app at it; the shell then starts (`initialize`) and push registers again for the new device (`PushSetup.ensureRegistered(force)`; the server ties a push registration to the request's device). Refusals are `:protocol`'s `PairError` sentences: a wrong or expired code (403 `invalid_code`), a code for another kind (409 `wrong_kind`), too many wrong codes (429 with `Retry-After`: "Try again in 2 minutes"), an unreachable server or something that isn't Dana. Pairing again with a new code removes the old device on its server with its own token afterwards (`PairingClient.remove`, `DELETE /api/devices/{id}`).
- **Settings → Server**: the paired server and "Paired as <device name>, <user>'s device"; **Pair again** (the form, server filled in) and **Unpair** (asks first): `DevicePairing.unpair`: `DELETE /api/devices/{id}` for this device with its own token, then the token and device are forgotten (the address stays for pairing again); offline it still unpairs and says to remove the phone on the Devices page.
- **The watch** pairs itself through the phone (`docs/wear.md` → Pairing): the phone answers `/pair_watch` with a code of kind `watch` it starts with its own token (`data/wear/WatchPairingOffer.kt`, `PairingClient.startPairing` = `POST /api/devices/pairings`).
- Tests: `app/src/test/.../pairing/PairingTest.kt` (the controller with fakes, the watch's offer against a MockWebServer), `PairingClientTest` / `PairingFlowTest` (the call and the form, shared with the kiosk and TV), `protocol/src/test/.../PairingTest.kt` (link parsing, code shape, answers, refusals).

## The app

- **Main screen (shell)**: `ui/shell/DanaShell` replaces the old tab bar on the phone (kiosk/TV never show `MainActivity`). Places: Now, Reminders, Notifications (badge = the overview's needs-you count, else `/api/now`'s; nothing at 0), Projects (only with `knowledge` → `docs/projects.md`), More (Shopping with the `shopping` addon → `docs/shopping.md`, Money with `money` → `docs/money.md`, Calls, People, About you → Settings; Memory only from About you). Shopping and Money take over More with their own list + stage under a "← More" link (`takeOver` in `OtherDestinations.kt`); `viewModel.addons` (`Me.addons`) decides which places and rows show. A `Destination.wide` place (Projects, Money) is drawn like SPLIT in unfolded landscape — the thread a sheet, the ask bar under the panes — so its content gets ~808dp beside the side pane; `ShellController.placeRef` is the on-screen context such a place sets (Money: `transaction` / `saving`). Layout by window width (`ShellLayout`): STACKED < 600 dp (cover: one column, list → stage drill-down, ask bar over a slim nav, thread as a sheet), SPLIT 600–899 (unfolded portrait: day strip, list | stage, thread as a sheet), FULL ≥ 900 (unfolded landscape: list + nav left, day strip over stage | thread, ask bar under the thread). All state (place, picks, thread open, ask draft) lives in `ShellController`, so fold/unfold keeps it; an unfolded auto-pick (first open reminder) is marked `auto` and does not drill in when folded.

Legacy screens hosted in a pane go inside `PaneWindow { }`, which narrows `LocalConfiguration` so they pick the layout that fits the pane. **No early `return` in a composable** (it crashed twice): branch into a child composable instead (`MoreItemStage`, `OpenReminder`, `DragChip`).

- **Chat stream**: every assistant request is a server-side *run* whose events (`run_id` + `seq`: `step_start`, `reasoning_delta`, `text_delta`, `tool_call`, `tool_start`, `tool_end`, `final`, prompts, `run_end`) stream over SSE and close with a `state` frame. `ChatController` composes the parts that render them: `ChatRunRenderer` maps each event onto `ChatTranscript` (the messages shown: reply bubbles grow per delta, a collapsible thought block, tool cards from the moment the model picks a tool, the typing indicator) and `ChatPrompts` (approval, choice, step limit), and drops replayed events by `seq` (`RunStreamClient`); `ThreadView` holds the thread's pages, memory and fresh view, `ChatVoice` push-to-talk, `ChatUndos` the Undo row, `ChatCache` the device copy, `ChatModels` / `ChatComposer` the input. `ChatRunRendererTest` and `ThreadViewTest` pin the reduction without a network. The SSE client times out after 45s of silence (server heartbeat every 5s). If the stream drops, it reattaches with `GET /api/sessions/{id}/stream?run_id=&after=<lastSeq>` and resumes; a session loaded while `running` attaches via its `active_run`. Push-to-talk voice defaults to **live device transcription** (`data/voice/DeviceSpeech`): the system `SpeechRecognizer` (Speech Services by Google, online: there is no offline model for many languages, Hebrew among them) listens in the user's languages from `/api/me` (`data/voice/SpeechLocales`: each code as a BCP-47 tag with a region — the phone's when it speaks that language, else the usual one — the first as the main language, switching between them on Android 14+; the phone's own locale when the user has none), streams partial words into a live user bubble, ends the utterance with its own endpointing, then sends the text as a normal `/api/assistant/message`. It falls back to the server path when the recognizer is unavailable or fails before any words; Settings → "Live transcription" (pref `live_transcription`) turns it off. The server path (`/api/assistant/voice_stream`, also used by the Wear app) streams PCM and gets the same run events back over the WebSocket. The chat model (`fast`/`balanced`/`deep`, from `GET /api/assistant/models`) is picked with the chip above the input and stored in prefs `chat_model`; the Wear bridge uses it too.
- **Screen as context in the power-button sheet** (server `docs/agent-actions.md`, `device_screen`): when the system opens the sheet with assist data (`SHOW_WITH_ASSIST`), `DanaVoiceInteractionSession` keeps the screenshot (`onHandleScreenshot`) and a text description of the app in front (`onHandleAssist` → `data/screen/AssistCapture` → `ScreenText`: app label, package, cleaned window title, Chrome's URL from `AssistContent.webUri`, visible text in reading order, no password fields, lines ≤600 chars, total ≤6000) in memory for that one opening only (`ui/viewmodels/ScreenShareController`, state machine `data/screen/ScreenShare`). Nothing is sent unless the **Screen** chip is on. It is off every opening and turns itself off after one message, typed or spoken, including one already in progress when tapped. `ChatController.screenAttachments` takes it when sending. **Paths:**
  - **Typed or device-transcribed with a screenshot:** multipart `POST /api/assistant/message_with_image` with `image` (JPEG, longest side 1280, quality 80) and a `device_screen` JSON string part.
  - **No screenshot:** JSON `POST /api/assistant/message` with a `device_screen` object (never the image in `images`; that endpoint has a 1 MiB limit).
  - **Server voice WebSocket (PCM):** `device_screen` in the stop frame, no image; shown as "text only".
  - On a 409 busy, no speech or an aborted recording, the screen goes back to the chip.
  
  **What the capture can't give:**
  - The system switches (`Settings.Secure` `assist_structure_enabled` / `assist_screenshot_enabled`, read through `getUserDisabledShowContext()`) explain themselves and offer the assistant settings.
  - Secure windows (FLAG_SECURE: banking, Chrome Incognito) hand over an all-black screenshot. `BlankFrame` treats that as none, and whatever exists is sent and named.
  - Opened from Dana (`AskDanaActivity` → `showSession` with `from_dana`, or Dana's own package in front), the chip is hidden.
  
  The sent bubble shows the screenshot from `cacheDir/sent_screens/` (files older than 1h are deleted) and a "Screen · App" caption. The label survives the thread reload only for the newest user message (`ThreadModel.carryScreen`), because the server doesn't mark screen turns. The approval card says "Asking because the screen was shared." from `approval_required.reason` or the pending payload's `approval_reason` / `untrusted_content`, and "Asking because this chat holds text others wrote." for `untrusted_result` (an email Dana read) and `untrusted_context` (a chat opened from a transaction). Kiosk and TV don't pass a controller, so they keep the old dock.
- **Offline queues** (`data/sync/`): reminder Complete/Snooze (phone alarm and watch) and the Reminders editor's field edits (kind `update`, partial `PUT /api/tasks/{id}`; consecutive updates to one task merge, newer keys win) go through `TaskActionQueue`. It tries once (6s), queues to `filesDir/pending_task_actions.json` if the server is unreachable or answers 5xx, and `PendingSyncWorker` (WorkManager) or the server coming back ONLINE flushes it. Call-recording uploads run in `CallUploadWorker` (network constraint, backoff, foreground `dataSync` job, Retry action), with handled recordings remembered in `filesDir/call_uploads.json`. WorkManager is the only library that brings Room, and only internally. **WorkManager starts on demand** from `DanaApp` (`Configuration.Provider`, default process = the package; the androidx.startup initializer is removed in the manifest) so it also works in the assistant sheet's `:session` process — content providers only run in the main process, and the sheet's `MainViewModel.initialize` → Inbox sync crashed there with "WorkManager is not initialized" (7.4.1–7.8.0). The TV flavor's `DanaTvApplication` extends `DanaApp`. Still no codegen in this project.
- **Reminders**: a `reminder` push event reaches `ReminderReceiver.show`, which also forwards the alarm to the watch (`WearReminderBridge`, `/wear/reminder_alarm`). Handling it on either device dismisses the other (`/wear/reminder_dismiss` phone→watch, `/reminder_dismiss` watch→phone).
- **Reminder alarm**: `ReminderReceiver.show` opens `ReminderActivity` directly with "Display over other apps" and posts quietly on `reminders_quiet` (the screen plays the alarm itself; no heads-up over it), else `reminders_channel` + full-screen intent. `ReminderActivity` (full-screen, over the lock screen: window flags, ringing, vibration) shows `ReminderScreen` (the UI), with the dial's option tree and geometry in `SnoozeDial.kt` and complete / snooze in `ReminderActions` (through `TaskActionQueue`). It uses the same Ink & Paper tokens as the app and follows the theme setting: one-tap time snoozes plus the hold-and-drag radial dial (time / zone arrive|leave / car / wake). Keep it on theme tokens — no hardcoded colours, gradients or glows. The dial sits low and its options fan **upward** (oval rings sized to the window by `SnoozeDialGeometry.fit`) so the thumb never covers them; while dragging, a readout at the top spells out the result ("When I arrive at Home"). Drawing (`layoutSnoozeFan`) and hit-testing (`selectSnoozePath`) share one geometry — change both together and keep `SnoozeDialTest` passing (it checks every node fits the Fold cover ≈555×876 dp and inner screen at 360 dpi). Short windows (< 780 dp) get a smaller title; wide landscape (≥ 720 dp) splits into two panes (row capped at 1100 dp, the dial centred in its pane). The alert and suggestions screens cap their column (680 / 760 dp, centred) on the unfolded screen.
- **Call recordings** (off until Settings → Call recordings → "Watch for call recordings"; Android doesn't let apps record calls, so Dana uploads what the phone's own recorder saves). **Folder**: turning it on opens the system folder picker (`ACTION_OPEN_DOCUMENT_TREE`, starting at Samsung's `Recordings/Call` when the phone has one); `RecordingsFolder` keeps a persisted read grant on that tree (no storage permission) and "Recordings folder" changes it. Settings also says which phones record calls at all (Samsung, Xiaomi, OnePlus / Oppo in their own dialers; Pixels and most others not, or only in some regions with an announcement), without promises. **Watching**: no foreground service; Android sends no change events for a picked tree, so `RecordingScans` scans it with `RecordingScanWorker` every 15 min (WorkManager, survives reboots), when the app comes to the foreground (`MainViewModel.onAppForeground`) and 10 s after a call ends (the phone-state broadcast `CallerCardReceiver` already gets). `FolderScan.plan` (pure) decides per file name against the handled-recordings file (`CallUploadStore`, `filesDir/call_uploads.json`): the first scan of a folder records what is there as seen (no burst of old calls; "Upload past recordings" sends them), a file changed in the last 20 s is still recording (another scan follows), a file the app was killed while handling (PENDING / NOTIFIED) is retried for three days, any other known state is never handled again. A file to handle is copied into `filesDir/call_recordings/` (the upload pipeline works on a `File` and must survive the app being killed; the copy is deleted after the upload or a skip, leftovers after two weeks). **Matching**: `RecordingNames.parse` reads the parts recorders put in file names — name, number, start time (Samsung `Call<name>_<yyMMdd>_<HHmmss>`, Xiaomi `<name>(<number>)_<yyyyMMddHHmmss>`, `<name> <yyyy-MM-dd HH-mm-ss>`, `Call_<number>_<date>-<time>_IN`, …) — and `CallMatcher` picks the call-log entry (`READ_CALL_LOG`): with a number, the answered call with that number closest in time (12 h); else the name's start time inside a call (3 min before its start to 2 min after its end), closest to its start; else the file's last change 2 min before to 10 min after a call's end. Missed calls never match. `RecordingInspector.inspect` (`data/sync/CallAutoUpload.kt`) adds the length (MediaMetadataRetriever). Calls ≥ `CallUploadSettings.thresholdSeconds` (10 s) upload by themselves, shorter ones (and every new one with auto-upload off) post an ask notification (Upload / Skip; tapping opens `ShortCallActivity`, a translucent sheet with preview playback and "Never upload calls with X"), contacts on the skip list are ignored. Settings → "Call recordings" holds the on switch (`CallUploadSettings.enabled`; `canWatch` = on and the folder still readable), the folder, the auto-upload toggle, threshold, Wi-Fi only, skip list and "Upload past recordings". **Past recordings** (`data/sync/PastRecordings.kt`): one unique worker, `PastRecordingsWorker` (work `past-recordings`, KEEP: tapping again never starts a second run; network constraint from Wi-Fi only, exponential backoff), sends the folder's old calls one at a time, oldest first, as far back as the user picks above the button ("How far back": last 7 days, 30 days (default), 3 months, everything, or "Since a date…" (the system date picker, up to today; the chip then reads "Since 3 Mar 2025"), by the file's last change; `PastRecordings.Range`, remembered in `CallUploadSettings.pastRange` / `pastSinceMs`). `PastRecordings.candidates` (pure) picks the audio the store knows as SEEN or NOTIFIED, or FAILED before the run started (new files, PENDING, QUEUED, UPLOADED and SKIPPED are not its business); each candidate's call and length are read in place (no copy: `RecordingInspector.durationSeconds(context, uri)`), contacts on the skip list are marked SKIPPED and calls under the threshold passed. Then per recording: copy it, upload it through `CallUploads.send` (the same code `CallUploadWorker` uses), release the copy, the store records UPLOADED or FAILED, the next. A rejected or unreadable file is marked FAILED and passed (no notification of its own; the next run tries it again); an unreachable server ends the attempt with a retry, and the next attempt continues from the store's states (`PastRecordings.tally` counts what the run already did, from the entries' `updated_at`); after 10 attempts it stops. No per-call result notifications for the backlog (the Calls screen has them). It runs as a foreground `dataSync` job with "Uploading past calls · 12 of 140" (Cancel = cancel the unique work) and posts one summary at the end ("Past calls uploaded: 138 uploaded · 2 couldn't be uploaded"). Settings reads the unique work's state (`PastRecordings.status`, pure `backlog`): while running "Uploading past calls… 12 of 140" (or "Waiting for a connection") with Stop; after a run "All recordings uploaded", or what failed / that it stopped, with the button to run again. New calls recorded meanwhile keep their own `CallUploadWorker`. Tests: `sync/PastRecordingsTest` (which files, the range, order, resume, a failure passed for the run and retried by the next, the Settings states). The Calls screen's "Select from recent recordings" lists the same folder. After an upload `CallResultWorker` polls `GET /api/calls/{id}` until the server's analysis is done and posts the result (title, labels, pending suggestions) with a Review action into `CallDebriefActivity`. Tests: `sync/CallMatchTest` (several recorders' names, the matcher), `sync/FolderScanTest` (the scan's dedupe, the share's parsing).
- **Call Debrief & suggestions**: `CallDebriefActivity` (standalone, `open(context, callId)`) shows summary, editable labels, key facts and the call's suggested reminders/events as cards (Create / Edit sheet / Ask assistant / Dismiss). Pending suggestions also appear on Now and on the call detail. "Ask Dana" anywhere (suggestion, call, task) opens the shared thread with that item on screen (`shell.openThread(ThreadContext)`); the thread shows the attached item as a `ContextAttachmentCard` with quick prompts. Other activities reach the main app with extras `open_context_kind`/`open_context_id` (context chat) or `open_call_id` (select a call in Calls). Their calls and wire classes live in `data/network/CallsApi.kt`; shared UI in `ui/components/SuggestionParts.kt`.
- **Foldable sizes**: a book-style foldable has a narrow cover screen (≈ 555×876 dp, COMPACT) and a near-square inner one (≈ 821×1088 dp, 1088×821 landscape, EXPANDED). Check new screens at both, e.g. on an emulator with `adb shell wm size 1248x1972` / `1848x2448` + `wm density 360`; cap reading columns (~720 dp) and sheets (~560 dp) on the inner screen (`widthIn(max).fillMaxWidth()` — in that order).
- **Sharing**: text, links and images shared from other apps land in the ask bar of the current thread, thread open. **Audio** ("Send to Dana", `ACTION_SEND` / `SEND_MULTIPLE` `audio/*`, phone flavor) opens `share/ShareAudioActivity`: `SharedAudio.pick` (pure) keeps the audio items (up to 20), each is copied into the app and gets a small sheet: "Which call was it?" with the answered calls of the last three days from the call log (the one `CallMatcher` matches first and picked; "Allow call log" when it isn't granted), "A call not in this list" (the file name's details) — picked by default when the file looks like a call recording — and, only with the `knowledge` addon in `/api/me`, "Not a call: just transcribe and keep it" with the user's active projects. A call goes through the same upload as a found recording (`CallUploads.enqueue`); a note is `SharedAudioNoteWorker` (`POST /api/entries` a note in the chosen project, then `POST /api/entries/{id}/files` the audio, which the server transcribes; WorkManager, retried while the server is unreachable). Upload / Skip this file / tap outside to drop the rest.

## Signals

What happens around the user, reported by the phone itself (server `docs/signals.md`, `POST /api/signals`): unlocks, screen time, getting in and out of the car, arriving at and leaving Dana's zones, the night's sleep from Health Connect. The phone app is the only source of these signals (the weather comes from Open-Meteo on the server); the tasks addon and the wake flow never ask where a signal came from. Phone flavor only: the platform glue is in `src/phone/.../data/signals/`, the kiosk and the TV get a no-op `PhoneSignals` (`src/nopush`); the pure parts and the queue are in `main` (`data/signals/`).

**Battery and privacy rules**: no foreground service and no continuous location. The app is woken by system broadcasts it is allowed to receive in the background, by Google Play services' geofences and activity transitions and by one WorkManager job; it never reads a location itself. The server only learns enter / leave (car, zone id), unlock times, when the screen was on and when a night's sleep started and ended: never where the phone is, which apps were used, any other health data, or the car's Bluetooth address (that stays in the app's prefs).

- **Queue** (`data/signals/SignalQueue`, `SignalSync`): every event goes into `filesDir/pending_signals.json` in the order it happened. `flush` sends batches of ≤ 200, oldest first (`api.signals.send`). A batch that fails (unreachable, 5xx, 408, 429) stays whole and goes again later; the server takes a repeated event without effect. Events the server rejects (`bad_event`, `unknown_zone`, `stale`) are dropped and logged; a 400 drops that batch; other refusals (unpaired, an older server without the route) keep the events without backing off. Events older than 47 h are dropped before sending (the server's limit is 48 h), and at most 5000 are kept. An event that should go now (car, zone, an unlock in the wake window) runs `SignalSendWorker` (network constraint, linear backoff, unique work REPLACE); the rest wait for the periodic run. The server coming back ONLINE and the app returning to the foreground flush too (`MainViewModel`).
- **Unlocks** (`data/wake/UnlockWatcher`): `ACTION_USER_PRESENT` can't be declared in the manifest, so it is registered at runtime by `DanaApp` and by the notification listener (which Android keeps bound). Every unlock is queued (at most one per 2 min; the server learns the wake window from them). Inside the wake window (the server's, cached in `SignalSettings`, refreshed daily and whenever the Signals page loads; 05:00–12:00 before the first) it is sent at once and the screen history is read 5 minutes later (`PhoneSignals.afterUnlock`), before the server's check ten minutes after the unlock. `adb logcat -s UnlockWatcher`.
- **Screen time** ("Wake from screen time", off by default; `ScreenTime`): with Usage access (Settings → Apps → Special app access; the switch opens that page) the app reads UsageStatsManager's `SCREEN_INTERACTIVE` / `SCREEN_NON_INTERACTIVE` events since the last read (Android 9+) and sends "screen" stretches. `ScreenStretches.read` (pure, `ScreenStretchesTest`) pairs on / off; a stretch still going on is sent up to the read and continues from there next time, so pieces never overlap. The history starts when the switch is turned on.
- **Car** ("Know when I'm in the car", off by default; `CarSignals`): two ways, both without a foreground service.
  - **Bluetooth**: "This is my car" picks one of the paired devices (`BLUETOOTH_CONNECT` asked then, Android 12+). `CarBluetoothReceiver` is declared in the phone manifest for `ACL_CONNECTED` / `ACL_DISCONNECTED`. Those are on Android's list of implicit broadcasts that manifest receivers still get, so the app is woken for them from the background on Android 8–16. A connect sends car enter, a disconnect car leave (`via: bluetooth`). CompanionDeviceManager presence (Android 12+) would need an association dialog and a companion service for the same result, and nothing on Android 8–11.
  - **Android Auto** puts the phone in car mode. `ACTION_ENTER_CAR_MODE` / `ACTION_EXIT_CAR_MODE` are not on that list, so they are watched by a runtime receiver (the app process and the notification listener). Each periodic run also compares `UiModeManager.currentModeType` with the last state sent, so a change made while no process ran still arrives, late (`via: android_auto`).
  - **Driving detection** ("Detect driving" under the car switch, off by default; `Driving`), for a car without Bluetooth: Google Play services' Activity Recognition transitions (`IN_VEHICLE` enter / exit, `play-services-location`) wake `DrivingReceiver` through an explicit mutable PendingIntent; no foreground service, no location. Turning it on asks for Physical activity (`ACTIVITY_RECOGNITION`, Android 10+). An enter is car enter, an exit car leave (`via: activity`). Android drops the registration on a reboot or an app update, so it is made again on app start (`PhoneSignals.init`) and after boot (`BootReceiver` → `PhoneSignals.onBoot`); turning the switch (or the car switch) off removes it.
  - **Bluetooth wins** (`DrivingRule`, pure, `DrivingRuleTest`): once the car chosen in "This is my car" has connected or disconnected since it was chosen, its connection alone says enter / leave and transitions are not sent. Before that (a car just chosen, or none) an enter goes unless the last activity event was already an enter, and an exit goes only after an activity enter; every Bluetooth report of the car forgets the activity state, so a ride whose enter Bluetooth took over never ends with a stray leave. Choosing another device, or "No device", makes the car's state unknown again.
  - A state already sent is not sent again (a flapping connection, or the periodic check after the receiver).
- **Places** ("Place reminders", off by default; `Places`): Google Play services geofences (`play-services-location`) for the zones from `GET /api/zones` (`GeofenceDiff.fences`: Home first, radius at least 100 m, at most 100). Turning it on asks for location in two steps: precise location while in use, then (Android 10+, after a short explanation) "Allow all the time", which Android 11+ grants on its own settings page. A crossing wakes `PlacesReceiver` (explicit mutable PendingIntent), which queues "zone" arrive / leave with the zone's id. No initial trigger: only crossings count. Geofences are registered on turning it on, on app start, after boot and app updates (`BootReceiver` → `PhoneSignals.onBoot`; Android drops them), afresh once a day, and when the `zones_changed` phone event arrives (`PhoneEvents`). Between those, `GeofenceDiff.diff` (pure, `GeofenceDiffTest`) only adds the zones that are new or moved and removes the gone ones; the registered set is kept in prefs. Location turned off (`GEOFENCE_NOT_AVAILABLE`) forgets them, and the next run registers them again.
- **Sleep** ("Wake from sleep data", off by default; `HealthSleep`): the `SleepSessionRecord`s a health app writes to Health Connect (`androidx.health.connect:connect-client`, phone flavor only), sent as "sleep" start / end (`via: health_connect`); the server takes a night ending in today's wake window as the wake, at that time, and a repeat without effect. The sleep comes from whatever writes it there: a watch's own health app (Fitbit, Samsung Health, Pixel Watch…) or the phone's. Dana's watch app needs no change and plays no part: the watch's health app syncs sleep to Health Connect on the phone. Turning it on asks Health Connect's own permission screen (`PermissionController.createRequestPermissionResultContract`) for `READ_SLEEP`, and for `READ_HEALTH_DATA_IN_BACKGROUND` where that Health Connect has the feature; without it Health Connect only answers while Dana is open, which the page says. Health Connect is an app on Android 9–13 and built in from 14: `HealthConnectClient.getSdkStatus` decides what the page shows: not available (Android 8, or no Health Connect for this phone; the switch is off and disabled), "Get Health Connect" / "Update Health Connect" (its store page, the web page without the Play Store), or the permission state with "Allow in Health Connect" and "Open Health Connect" (its settings). Every call is guarded: a missing or outdated Health Connect never crashes. Health Connect shows why Dana asks from `HealthPermissionsActivity` (the rationale action on Android 13 and older, the `VIEW_PERMISSION_USAGE` alias on 14+; without it Health Connect won't show its permission screen). Reads cover the last 47 h; `SleepSessions.read` (pure, `SleepSessionsTest`) keeps the sessions written after the cursor (the latest write time read so far, `SignalSettings.sleepCursor`), so a night a watch syncs hours late still arrives once and a session read again is not sent again. It skips what the server would refuse (an end before its start, over 24 h, in the future, older than 47 h) and gives one event for the same night written by two apps. The cursor starts when the switch is turned on. Reads run in the periodic run, right after an unlock in the wake window, and when the app comes to the foreground (`PhoneSignals.onForeground`, one-time `MODE_SLEEP` runs).
- **Periodic run** (`SignalsWorker`, network constraint): every 15 min with screen time on, else hourly. It reads the screen history and the sleep sessions, compares car mode, refreshes the cached wake window once a day, brings the geofences in line, and flushes the queue. One-time runs of the same worker do one part: after an unlock (screen, sleep), in the foreground (sleep) and for the geofences (places, places afresh, places off).
- **Signals page** (Settings → Signals, `MoreItem.SIGNALS`, Back to Settings; `ui/screens/signals/SignalsScreen`, `SignalsController`): `GET /api/signals` shows each signal (Waking up, Screen time, Car, Places, Sleep, Weather; unknown ones by name) with its sources, highest rank first. The one in use has an "In use" pill, each source shows its last report ("Last · 07:12 · unlock"). Under them are the phone sources' switches with their permission state and a button for what is missing (usage access, Nearby devices, physical activity, location / all the time, Health Connect; re-read on resume): Waking up has "Wake from screen time", Car "Know when I'm in the car" with "This is my car" and "Detect driving", Places "Place reminders", Sleep "Wake from sleep data". The wake window shows its two times (tap to change: `PUT /api/profile {wake_window}`) and "Use the learned one" when it was set by hand (`wake_window: null`). The phone's switches show even when the overview can't load.
- Tests: `app/src/test/.../signals/` (`SignalQueueTest`: order, batch size, retry, rejected, stale, restart, the body's shape; `ScreenStretchesTest`; `GeofenceDiffTest`; `DrivingRuleTest`; `SleepSessionsTest`; `SignalsContractTest` decodes the server's `server/tests/fixtures/signals_web.json`).
