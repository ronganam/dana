# People, call card, wake briefing, weekly review

## People (`addons/people/`, web `static/people.js`)

Code: `values` (tuning, normalisation, formatting), `activity` (every read / write of calls and notifications), `store` (people and numbers, lookups), `linking`, `merge`, `person_tasks`, `cadence` (cadence, drifting, the People list), `briefs`, `detail` (a person in full, the call card, the context chat), `api` (`/api/people*`), `tools`. Tests: `bin/test test_people`, `bin/test test_people_users`.

- **Per user** (table in the addon's `migrations/m0001_baseline.py`): people and their numbers, aliases, pinned / hidden flags, cached briefs and their signatures belong to a user (`user_id`); every function takes the `User` it answers for, and another user's person id answers like an unknown one (None / "not found" / 404). A phone number is unique per user, not across users: two users may each have a person with the same number, and the call card, `resolve` and linking answer from the caller's own numbers. Merge works only within one user's people. No sharing. A user without `people`: the tools are not offered, `/api/people*` answers 403 `not_connected`, and composers (search, briefing, weekly review, meeting cards, the call pipeline's people context, approval card names) skip people.
- **Tables**: `people` (`user_id`, name, `aliases` JSON, relation, notes, birthday `YYYY-MM-DD`/`MM-DD`, `emails` JSON, pinned, hidden, `source` auto|manual, cached `brief`, `contact_resource`: the Google contact it was filled in from) and `person_phones` (`user_id`, phone → person, primary key `(user_id, phone)`; digits with country code, e.g. `972501234567`; `DEFAULT_COUNTRY_CODE`, server-wide, no default: set to 972 it turns `050…` into `97250…`, unset a local number is stored as typed). `phone_calls.person_id` / `notifications.person_id`: NULL = not checked yet, `''` = checked, no match; a person id belongs to one user.
- **Whose activity**: which calls and notifications belong to a user is decided in exactly two functions, `activity.calls_sql(user)` / `activity.notifications_sql(user)`; every people read and the linking go through them. Both are per user (`user_id = ?`, the phone phase), so nothing is ever linked into another user's people, briefs or call card.
- **Linking** (`linking.link_pending(user)`, run on every people read, after each processed call (`briefs.after_call(user, call_id)`) and by the brief job): the user's calls match their people by number, then by contact name (and the number is added to that person); a call from someone new **creates** a person (`source=auto`; number-only callers are created `hidden`). For a user with `contacts`, a caller the call does not name is called what their Google contacts call that number (`addons.contacts.store.caller_name`): the person is created with that name and shown, or the number goes to the person who already has that name. Notifications only match existing people by `sender` (or a 1:1 `conversation`), names compared without case/emoji/punctuation; no people are created from notifications. Changing names/numbers or creating/merging rechecks the user's unmatched rows. Deleting a person leaves their activity unmatched.
- **Google Contacts** (`docs/contacts.md` → People): for a user who also has `contacts`, after every contacts sync a person whose number is on one of their contacts takes from it what the person lacks — the name of an auto-created number-only person (which is then shown), the contact's other numbers no other person has, the birthday and the emails when empty — and remembers the contact (`store.fill_from_contact`). A name, birthday, email or note the user typed is never changed; no person is created from a contact. A merge keeps both people's emails.
- **Cadence**: contact days (calls + messages, last 365 days); with ≥ 4 gaps the median gap is the typical gap; `drifting` when the days since last contact exceed `max(PEOPLE_DRIFT_MIN_DAYS (14), 2.5 × typical)`. Messages only exist for 30 days (notification retention), calls forever.
- **Tasks per person**: among the tasks the user can see, `task_links` with `ref_type='person'`, tasks linked to their calls, and open tasks whose title contains one of their names (whole words, ≥ 3 letters). A person link is made only to one of the user's own people (`POST /api/tasks/{id}/links {ref_type: "person"}`: another user's person 404, without `people` 403 `not_connected`; `link_task_to_person` resolves among the caller's people) and resolves only for the person's owner (`tasks.links.links_for_tasks(user, …)`: on a shared list, someone else's link to one of their people is left out).
- **Brief**: the model (`BRIEFING_MODEL`) writes `points` (what's going on) + `open` (open loops), Hebrew or English by the content's letters, for the person's owner (their profile, `core/user_profile.for_user`: name, pronoun and context; docs/access.md → User), as that user (usage rows are theirs). Cached with a signature of the last 8 calls, 30-day message count, open task ids, relation and notes; the `refresh_briefs` job (`hooks.py`, every `PEOPLE_BRIEF_INTERVAL_SECONDS`, 600) runs `briefs.refresh_briefs(user)` for every user with `people`, each as that user, one after another: it rewrites up to `PEOPLE_BRIEF_BATCH` (6) of their stale ones, newest contact first; one user's failure does not stop the next. A processed call schedules its person's at once. A failed rewrite keeps the old brief. People with no calls and < 3 messages get none.
- **Merge candidates**: same normalised name, one name inside the other, Hebrew→English transliteration, or ≥ 0.88 similarity, among one user's people. The web list offers Merge / Not the same (the latter remembered per browser).
- **API** (for the request's user, who needs `people`): `GET /api/people?q=&sort=recent|pinned|drifting|name&hidden=1`, `POST /api/people`, `GET|PUT|DELETE /api/people/{id}` (PUT: `name`, `aliases` (replace), `add_alias`, `phones` (replace), `add_phone`, `relation`, `notes`, `birthday`, `emails` (replace), `pinned`, `hidden`; a rename keeps the old name as an alias; a person's payload has `emails`), `POST /api/people/{id}/merge {other_id}`, `GET /api/people/merge-candidates`, `POST /api/people/{id}/brief` (rewrite now), `GET /api/people/{id}/card`. Context chat: `POST /api/chat/context {kind: "person", id}`. Task link: `POST /api/tasks/{id}/links {ref_type: "person"}`.
- **Agent tools**: `list_people`, `get_person` (read), `update_person`, `link_task_to_person` (write).

## Incoming-call card

`GET /api/people/lookup?phone=` → `{found, card}` for the request's user, from their own people only: plain DB reads + the cached brief, never a model call (the phone asks while it rings). The card: name, initials, relation, `headline` ("Last spoke 12 days ago"), up to 2 brief `points`, up to 3 `open` items (brief open loops + open tasks, near-duplicates dropped), `last_call` {title, summary, ago}, counts, upcoming birthday, `drifting`. Numbers match exactly or on the last 9 digits when that's unique among the user's numbers. Unknown numbers and number-only people without a processed call → `found: false`, unless the user has `contacts` and their Google contacts name the number: then the card has that name, the headline "In your contacts", an empty `person_id` and nothing else (no person is made). The Android app shows it as a floating card over the dialer and forwards it to the watch (Android repo `docs/phone.md`).

**Meeting cards** (`core/briefing.py::meeting_cards_loop`, every 2 min, `MEETING_CARDS=0` turns off; for every user with `calendar` and `phone`, each as that user with their own people, calendar and phone (`core/composers.for_each`); a failing user backs off 15 min (`MEETING_BACKOFF_SECONDS`) and does not stop the next): `MEETING_CARD_MINUTES` (10) before a timed event whose title or attendee names contain a known person's name, that person's card is pushed as a `context_card` event `{reason: "meeting", event_title, starts_at, minutes, card}` (only when the card has something to say; once per event).

## Wake briefing (`core/briefing.py`; routes in `core/briefing_api.py`)

- **Wake detection** (`core/wake.py`, a composer, per user; only for a user with `phone` **and** `homeassistant` connected: without them an unlock answers `unavailable`, nothing is recorded and the poll skips them; once a day per user inside `WAKE_WINDOW_START_HOUR`–`WAKE_WINDOW_END_HOUR`, 5–12). An unlock is the request user's own signal. Once confirmed, that user's wake-trigger tasks fire (`triggers.fire(user, "wake")`) **and** their briefing goes out; the day is stored as their `wake_log` row (one per user and date, `INSERT OR IGNORE`: the "once a day" record; migration `m0015_composers_per_user` moved the old `last_wake_trigger_date` memory there). The last raw signal is `system_marks['wake_signal:<user>']`; a check in flight is kept in memory per user. There are three signals:
  - **Phone unlock** (main): the Dana app reports unlocks (`POST /api/phone/unlock {at}`, from `UnlockWatcher` in the Android repo). `WAKE_CONFIRM_SECONDS` (600) later, `handle_wake` reads the phone's screen history from the user's own Home Assistant (`/api/history/period`, their setting `phone_interactive_sensor`).
    - Screen on for at least `WAKE_MIN_SCREEN_SECONDS` (90) since the unlock: confirmed.
    - Less than that: nothing is stored, and the next unlock tries again.
    - HA unreachable: the unlock is trusted.
    - Unlocks are used because the 07:30 alarm keeps the screen "on" for 3–10 min while it rings, but it never unlocks the phone.
  - **Fallback poll** (`wake_watch_loop` → `poll_once`, every `WAKE_POLL_SECONDS`, 300, for every user with the flow, each as that user, one failing not stopping the next): the screen was on for at least `WAKE_FALLBACK_SECONDS` (360) across at least `WAKE_FALLBACK_SESSIONS` (3) stretches within the last 30 min. Replayed on Nov 1–11 2026, it never fired on the alarm alone, and fired 10–40 min after real wake-ups.
  - The old `wake_up` webhook (from the HA custom integration `ganam_assistant`) is gone with `/webhook`: a screen-on signal also fires on the alarm, and its config once pointed at the old phone's sensors, which is why no wake fired between 2026-08-22 and 7.15.
- **Who gets one** (`briefing.available`): a user with `phone` (pushed there), or with a Telegram chat and at least one of `phone`, `calendar`, `tasks`, `people`, `homeassistant`. `GET /api/briefing/today` answers `{"briefing": null}` for anyone else; `POST /api/briefing/generate` 403 `not_connected` (`phone`).
- **Content** (`gather(user)`, the user's own addons only; a missing addon adds nothing): today's events (the user's own `calendar` addon: their selected calendars, declined/cancelled dropped; none without it — the prompt then says the calendar could not be read), tasks due today/overdue + undated high priority + today's time reminders (own and shared lists), pending suggestions and the Inbox needs-you count + cached overall summary (with `phone`), weather from the user's Home Assistant (their setting `weather_entity`, default `weather.forecast_home`; today's high/low/rain via `weather.get_forecasts`; none without the addon), birthdays within 3 days and up to 2 drifting people (with `people`). The model (`BRIEFING_MODEL`, as the user: usage rows theirs) writes, for the user (their profile, `core/user_profile.for_user`: name, pronoun, context; the first admin's prompt is byte for byte the old one), `headline` + 3–6 `points` in `BRIEFING_LANGUAGE` (English; names/titles kept as written); on failure a plain version is written from the same data.
- **Storage / delivery**: one `briefings` row per user and local date. `briefing` push event `{date, headline, points, next_event, due, needs_you}` (the phone shows an expandable notification and forwards it to the watch); `BRIEFING_TELEGRAM=1` also sends it to the user's Telegram chat (`core/notify.py`). Pushed once a day; a briefing made earlier by the fallback is rebuilt with fresh data on wake.
- **Fallback** (`fallback_loop` → `fallback_once`): at `BRIEFING_FALLBACK_TIME` (10:00), for every user who gets one and has none yet (each as that user, one failing not stopping the next), one is made (not pushed) for the app, widgets and dashboard. `GET /api/briefing/today?generate=1` makes it on demand (app open). `POST /api/briefing/generate {deliver}` rebuilds it.
- **Surfaces**: web Reminders screen (Today strip until 14:00, hideable per day), bedroom dashboard tasks card (until noon), phone widget + watch tile (Android repo).

## Weekly review (`core/weekly_review.py`, web `static/review.js`; routes in `core/briefing_api.py`)

- **Who**: every user with `tasks` (`weekly_reviews.user_id`; the routes answer for the caller: `GET /api/review/latest` null without `tasks`, the others 403 `not_connected` `tasks`, another user's review id 404). Suggestions only with `phone`, people only with `people`, next week's events from their own `calendar`. The prompt is written for the user (`user_profile.for_user`; the first admin's byte for byte); the model call is theirs.
- **When**: `WEEKLY_REVIEW_AT` ("sat 20:00", local); missed by a restart → made until noon the next day (`schedule_once`: each user as themselves, one failing not stopping the next). One per user and ISO week (`weekly_reviews.week`); generating again supersedes their pending one.
- **Items**: overdue tasks; tasks snoozed ≥ `REVIEW_SNOOZE_MIN` (3) times (`tasks.snooze_count`, +1 per `POST /api/tasks/{id}/snooze`); tasks untouched ≥ `REVIEW_STALE_DAYS` (21) without a future time trigger; suggestions pending ≥ `REVIEW_SUGGESTION_DAYS` (7); up to 3 drifting people. Max `REVIEW_MAX_ITEMS` (25). Plus the week's stats and next week's events per day.
- **Proposals**: the model (`BRIEFING_MODEL`) picks one allowed action per item — task: `complete|reschedule|delete|move_group|keep`; suggestion: `accept|dismiss|keep`; person: `reach_out|keep` — with a reason, a future `due_date` / an existing `group`. Invalid answers fall back to defaults (overdue → reschedule to Sunday, old suggestion → dismiss, person → reach out Sunday, else keep). `keep` items start unticked.
- **Apply**: `POST /api/review/{id}/apply {items: [{ref, action, due_date, group, enabled}]}` (client choices override; omitted = stored proposals). Reschedule resets `snooze_count`; complete/delete push `reminder_clear`; reach out creates "📞 Reach out to X" (Personal, low) linked to the person. Result stored; a review applies once. `POST /api/review/{id}/dismiss`, `GET /api/review/latest|{id}`, `POST /api/review/generate {deliver}`.
- **Money** (users with `money`): a section built by `queries.week` (`core/weekly_review.py::money_week`): spent this week vs a usual week (median of the last 8), the top 3 groups, new recurring charges and price changes; in the model prompt, the review chat and the payload's `money` field (null when there is nothing to say: no spending and no recurring news), and a money line in the summary without the model.
- **Delivery**: `weekly_review` push event `{id, headline, items, proposed, summary}` + a Telegram message to the user's chat (`core/notify.py`; `REVIEW_TELEGRAM=0` turns it off). Context chat `kind: "review"`.
