# Phone notifications Inbox + direct push

Server side of the notification pipeline: the `phone` addon (`addons/phone/`): `push.py` (direct push), `notifications/` (`ingest`, `store`, `processing` = triage + suggestions, `triage` (questions + decisions), `judges` (who answers them), `rules`, `buckets`, `shade`, `escalation`, `actions`, `digest`, `retention`, `summary`, `overview`), `suggestions.py` (reading suggestions), `popups.py` (the suggestion pop-up), `notification_tools.py` (agent tools), `config.py` (the addon's name, the per-user loop helper and self-check marks); handlers in `notifications/api.py` (the Inbox, rules, actions) and `api.py` (suggestions, push devices, `POST /api/signals`: the phone's signals, `signals.py`, `docs/signals.md`); web Inbox `web/inbox.js` (the addon's page); app icons `app_icons.py`. The phone side is in the Android repo's `docs/notifications.md`.

**Per user.** Everything here belongs to one user: a paired device (core's `devices`, `docs/devices.md`) registers for push with its own token (`phone_push`, keyed by the device), push events are queued for one user (`phone_events.user_id`) and fetched only by them, and notifications, rules, summaries, declines, action requests and the digest state carry `user_id`. Every `/api/notifications/*` and `/api/phone/*` endpoint answers for the caller and needs the `phone` addon (403 `not_connected` without it); another user's id answers like one that does not exist (404). Every function takes the `User` first (`ingest(user, …)`, `list_notifications(user, …)`, `push.send(user, type, data)`); background work runs as that user (`users.acting_as`), so model and TypeSafe usage rows carry them. The loops (retention, digest, re-nudge, triage retry) run once per user with `phone` (`config.for_each_user`, each as that user, a failing one logged and the next still run); summaries refresh per user; triage queues and batches are per user (a judge call carries one user's notifications, worded for them) and triage interrupted by a restart resumes per user at startup. In-memory state is per user (escalation rate limit, summary refresh task / back-off). Prompts (triage questions and state, extraction, summaries) are written for their user from their profile (`core/user_profile.py::for_user`: name, pronoun, "About <first name>:" + their context when they have one); the first admin's are byte-for-byte as before. The same notification on two people's phones (a shared group) is stored once for each (`UNIQUE (user_id, content_hash)`). Tuning values (`NOTIFICATION_*`, `SUGGESTION_POPUP*`), the triage model, the TypeSafe key and the FCM key stay server-wide env; push registrations are per device (`phone_push`: transport + address, phone migration `m0003`).

## Phone notifications Inbox

- **Capture** (Android phone flavor, `DanaNotificationListener` + `NotificationSyncWorker`): needs "Notification access". Skips ongoing / foreground-service / progress / group-summary notifications, Dana's own, a per-app deny list and (default on) banking / authenticator apps; one-time codes are replaced by `[code]` on the phone (and again on the server). A durable outbox (`filesDir/notification_outbox.json`) batches them to `POST /api/notifications/batch {posted, removed, active_keys}`; removals carry the shade reason (`click` → opened, `cancel` / `cancel_all` → swiped, `dana` → dismissed; `app` (cleared by its app — read there or elsewhere; chat apps also cancel a moment before the system logs a tap) → archived, out of the Inbox; `timeout` stays) and the raw Android `code` (unmapped ones are logged).
- **Store** (`notifications/ingest.py` writes, `notifications/store.py` reads): one row per distinct content per user (`content_hash`); a newer content under the same shade key archives the older row (`removed_reason='updated'`, kept and searchable). FTS in `notifications_fts`.
- **Events**: `processing.schedule` emits `phone.notification.ingested` (`ids`) via `core.events.emit` before triage, in the background as the user; an error is logged and never holds up the pipeline. The phone addon imports none of its listeners; money listens with `@addon.on("phone.notification.ingested")` (`addons/money/hooks.py`) for Google Wallet payments (`docs/money.md` → Instant updates from the phone). The bank / card apps themselves never reach the Inbox: with `money` the phone sends them to `POST /api/money/signals` instead.
- **Triage** (`notifications/triage.py`: the questions, worded for the user's first name (`questions(me)`), and the decisions): Choice `category`, Score `priority` (0–4), Nouls (probability of yes) `needs_action` / `from_person` / `time_sensitive` / `urgent_request` / `promotional`, plus the to-do gate: `owner_wrote_it` / `addressed_to_owner` / `tracked_elsewhere` (work tools, calendar) / `record_only` (receipts, statements) / `self_clearing` (device states) — optional in an answer, missing = unsettled. `decide()` is the truth table → `priority` (urgent = important AND time-sensitive), `bucket` (`needs_you` | `normal` | `dismiss`), `extract`, `escalate`; it is the one place decisions are made and does not know which judge answered. Rules (`notification_rules`, per app or app+sender: `mute` → dismiss bucket without asking a judge, `important` → needs_you) and low engagement (≥ 10 handled, ≥ 90 % swiped) feed it. Changing or removing a rule re-buckets the app's active notifications from the stored answers (`buckets.stored_answers` → `decide()`, no judge call; `buckets.reapply_rule`), so un-muting an app puts them back where the triage put them; ones muted at ingest (never answered) get their first triage. Feeds (`social_media`, `news`) never reach `needs_you`, escalate or extract unless a person asks for something or the app has an `important` rule (alarming fake posts).
- **Judges** (`notifications/judges.py`; `judges.judge()` picks one, read on every call): a judge takes one user's notifications and returns the answers per notification id in the shape `decide()` reads.
  - **The LLM** (default): the background model through `core/llm.complete_json`, purpose `notification_triage` (model: `MODEL_NOTIFICATION_TRIAGE` → `NOTIFICATION_MODEL` → `BACKGROUND_MODEL` → Claude Haiku; Claude thinks at low effort), up to `NOTIFICATION_TRIAGE_BATCH` (10) notifications per call. The prompt is built from the same `questions()` (every question, its levels / yes and no criteria) plus the user's profile and the time, and asks for strict JSON `{"judgments": [{id, category, priority 0–4, <each Noul question>: 0–1}]}` per prompt id (`n1`, `n2`… mapped back in code). Notification text is untrusted: it goes in a `<notifications>` block, one JSON object per line with `<` escaped (no text can close the block), and the prompt says it is data to judge, never instructions. A judgment with an unknown id, a category outside the list, a priority outside 0–4, a missing required answer or a probability outside 0–1 is dropped, and so are both answers when an id comes twice. Cost: the instructions are ~1.6k tokens once per call and a notification ~50–150 more, so at 10 per call about 250 input tokens per notification; each judgment is ~90 output tokens, plus the model's thinking. Usage is filed under `notification_triage` with `ref` `notification:<id>` (one) or `notification_batch:<n>`.
  - **TypeSafe** (Jev, when `TYPESAFE_API_KEY` is set: cheaper, and its probabilities are calibrated): one request per notification with all questions bundled (~0.2 s; its API judges one state at a time), tracked as a `decision` in `core/usage.py`.
  - **Queue** (`notifications/processing.py`): `schedule` queues the new ids per user; a worker hands them to the judge a batch at a time, at most `NOTIFICATION_TRIAGE_CONCURRENCY` (4) batches at once across users, taking the next batch only when a slot is free, so what arrives meanwhile goes in the same call. A notification the judge did not answer (the call failed, or its judgment was missing or malformed) stays `triage_status='pending'` (`bucket='normal'`, never a guessed answer) with `{"error", "attempts"}` in `triage`; every 5 minutes `retry_pending` queues the user's pending ones from the last 24 h not tried in the last 2 minutes, and the third unanswered attempt marks it `failed`. Pending / failed ones from the last 24 h also resume on startup (per user); `POST /api/notifications/{id}/triage` reruns one. The stored `triage` names the judge's `model`.
- **Suggestions** (`notifications/processing.py`; read through `suggestions.py`): `extract` = has an action AND not the user's own message AND not clearly for someone else AND not tracked elsewhere / a record / a self-clearing state (Noul ≥ 0.7 blocks, unsettled doesn't), never for security / promotion / calendar reminders. Tuned on the first 21 resolved suggestions (17 were dismissed: CI/PR/Jira items, receipts, device states, the user's own message). Then the model (`NOTIFICATION_MODEL`) returns action items (prompt: most notifications need none; explicit skip list; at most one trigger, enforced in code: time > location > car > wake) → rows in `call_suggestions` with `source_type='notification'` (`call_id` holds the notification id; API returns `call_id: null`, `source_type`, `source_id`, `notification{}`). Same accept/dismiss endpoints; accepted tasks get a `task_links` ref `notification`. A notification's suggestions belong to the notification's user (`suggestions.visible_sql`: listed, fetched, accepted, dismissed and counted only for them; another user's → 404); call suggestions are not per user yet (the calls phase). A notification suggestion whose notification was deleted (retention keeps accepted / dismissed ones) belongs to nobody and is no longer listed. Notification suggestions don't open the phone's full-screen suggestions pop-up (`suggestions` push) unless `SUGGESTION_POPUP_NOTIFICATIONS=1` (default 0): they wait in Now's quiet list (`docs/now.md`); calls still pop up. `GET /api/suggestions` defaults to `source=call` (older apps); pass `source=all|notification`. `POST /api/suggestions/bulk {ids, action: "dismiss"}`.
- **Suggest-only**: nothing is dismissed automatically. `POST /api/notifications/status {ids | package | bucket, status: dismissed|archived|active}` (`package` = everything active from that app; `bucket: "dismiss"` = the noise, which also covers everything from quiet (`mute`) apps and muted senders) returns `device_keys` the phone cancels in its shade and an `undo_id` (`POST /api/undo/{id}` restores the rows and their suggestions in Dana; it doesn't bring them back to the shade); dismissals made elsewhere (web, agent `dismiss_notifications`) reach the phone as `cancel_keys` in the next batch response (also for keys the phone reports in `snoozed_keys`, so a dismissed snoozed one doesn't come back).
- **Snooze** (`snoozed_until`, UTC ISO): `POST /api/notifications/snooze {ids, until? | minutes? | clear?}` → `device_keys [{key, until_ms}]`; the phone snoozes them with Android's own snooze (removal reason `snoozed` is ignored on ingest). Snoozes made on the web / by the agent reach the shade as `snooze_keys` in the next batch response. Snoozed rows leave `active` lists, counts and the digest, show under `status=snoozed` (`counts.snoozed`), and are active again once the time passes; any status change clears the snooze. Agent tool `snooze_notifications` (write).
- **Escalation**: urgent ones (not calendar reminders, not muted) — important AND time-sensitive, or a person in a chat with the user saying it's urgent (Noul `urgent_request`: "דחוף", "ASAP", "תענה"; not apps or feeds) — and every one from an app/sender with the `alert` rule, are announced (`notifications/escalation.py`). **Re-nudge until seen** (`renudge_loop`, every 30 s): at `NOTIFICATION_RENUDGE_MINUTES` (default `3,10`) after the first alert, the alert is sent again (`attempt` extra, newest text in that chat) unless it was seen: opened / swiped / dismissed / snoozed, cleared by its app (read in the app, maybe elsewhere), or `POST /api/notifications/seen {ids}` from the alert screen (Open / Ask Dana / Got it) → `seen_at`; `nudges` counts them. Default (`NOTIFICATION_ALERT_STYLE=screen`): an `alert` push event (notification_id, key, package, app, title, text, priority, emoji, attempt) opens the phone's full-screen alert (open in app / snooze / dismiss / Ask Dana). `notify`: a `notify` event titled `⚡ Dana:` on the `important` channel (dropped on ingest to avoid a loop). Either way, max `NOTIFICATION_ESCALATIONS_PER_HOUR` per user. Only fresh ones: posted ≤ `NOTIFICATION_ESCALATE_MAX_AGE_SECONDS` (900) ago are announced and ≤ `NOTIFICATION_EXTRACT_MAX_AGE_HOURS` (12) get suggestions — the first sync after granting access delivers the whole shade.
- **AI summaries** (`notifications/summary.py`, per user: each user's own notifications, cached under their id, their own refresh task and back-off): one model summary per app with ≥ `NOTIFICATION_SUMMARY_MIN_ITEMS` (2) active notifications (who wrote what, what needs the user first; the needs-you ones are given as a separate "Waiting for <first name>" list, never as a per-line tag — the model echoed the old "[needs <name>]" tag into the points — and `clean_point()` strips any such tag for that name from what is stored and returned, old cached text included) plus a 1–2 sentence Inbox briefing. Cached in `notification_summaries` (key: user + scope = package or `_overall`) with a signature of the notifications they cover; only apps whose notifications changed are rewritten, each in its own call (it sees only that app's notifications — one combined prompt let flash-lite mix people between apps), then the briefing from the app summaries + the needs-you items (`NOTIFICATION_MODEL`). Each summary is 1–3 short bullet points (briefing 2–4), stored newline-joined in `summary` and returned as `points`; written in the user's first language (`language(user)`, `core/user_locale.py`), whatever language the notifications are in, names and quotes kept as written. `STYLE_VERSION` (now 4) and that language are part of every signature: bump the version when the prompt or format changes, and a change of the user's language rewrites the caches. `GET /api/notifications/summaries[?refresh=1]` never waits: it returns the cache (`stale` per entry, `refreshing`) and starts a rewrite in the background, at most every `NOTIFICATION_SUMMARY_MIN_SECONDS` (45; ~5 min after a failure). Agent tool `summarize_notifications`.
- **Digest** (`notifications/digest.py`): at `NOTIFICATION_DIGEST_TIMES` (once per slot per day) to each user with `phone`, on their Telegram chat (`core/notify.py`) + their phone (`notify` event, `digest` channel), only when something needs them, a suggestion of theirs waits, or ≥ 5 are suggested to dismiss. When each user's slots last fired and what their last digest covered is in `notification_digest_state` (slot `HHMM` → date, `last` → local ISO time; moved from the old `notif_digest_*` rows of `memories` by m0013). Preview: `GET /api/notifications/digest?hours=12`.
- **Buttons from the web** (`notifications/actions.py`; the `actions` column: the phone sends each notification's buttons, max 6 `{title, reply}`; `on_phone` = still in the shade, not snoozed): `POST /api/notifications/{id}/act {action: "open" | <button title>, text?}` → 202 stores a row in `notification_action_requests` and pushes a `notification_action` event to the user's phone carrying **only** `request_id` (the phone fetches `GET /api/notifications/requests/{rid}` with its token, presses the button, `RemoteInput` text for replies, then `POST .../requests/{rid}/result {ok, error?}`) — the reply text never goes through Google. Requests expire after 120 s (`expired`); a done one sets `seen_at`. On the phone the Inbox presses them directly through the listener.
- **Web Inbox** (the phone addon's page: `addons/phone/web/inbox.js` + `inbox.css`, registered with `Dana.panel` as `inbox`, `/#inbox`): views Needs you / Everything / Suggested to dismiss / Snoozed / Dismissed, search, group by app with the AI summary per app + the "At a glance" briefing, suggestions (create / edit / dismiss / Ask Dana), multi-select (shift-click range) with bulk dismiss / snooze, undo toasts, detail pane with the phone's buttons + reply box, snooze presets, per-app rules and Ask Dana. Keyboard: j/k, Enter, e, s, x, o, a, /, g, 1–5, r, ?, Esc. Each app's tile is its icon (App icons, below) over its letter. Polls every 20 s while open; its navigation badge = needs-you + pending suggestions (every 60 s while it is not open).
- **Other endpoints**: `GET /api/notifications?status=&bucket=&category=&package=&q=&since=&limit=` (+ `counts`), `GET /api/notifications/{id}`, `GET /api/notifications/apps` (per-app counts + rules), `POST /api/notifications/rules {package, sender?, action: mute|important|alert|none, apply?}` → `{…, reapplied, moved, message, undo_id}` (undo restores the previous rule and the buckets it moved; `buckets.change_rule`, shape in `docs/now.md`), `DELETE /api/notifications?package=` (keeps task-linked rows). Chat context kind `notification` (`POST /api/chat/context`).
- **Notifications screen** (phone, `notifications/overview.py`): `GET /api/notifications/overview` → counts (`total`, `noise`, `needs_you`, `snoozed`), apps with something waiting (rule `alert` / `normal` / `quiet`, needs-you / noise counts, cached AI summary points or the newest notification), `quiet_apps` (muted apps, even with nothing waiting) and `rule_suggestions`: apps with no rule that pass the low-engagement test (≥ 10 handled in 30 days, ≥ 90 % swiped), max 3. `POST /api/notifications/rule-suggestions {package, accept}` → accept sets the `mute` rule and re-applies it; decline is stored in `notification_rule_declines` and not offered again for 60 days; both return `undo_id`. Exact shapes in `docs/now.md`.
- **Health marks** (per user, `config.mark`): every batch marks `notification_sync:<user id>` and every `push.send` marks `push:<user id>` (ok / failed + why: no phone registered, FCM not configured, rejected; each device's transport is listed) in `system_marks`; `core/checks.py` reads the caller's (`push`, `notification_sync`, `triage`; "not connected" without the addon), shown by `GET /api/checks` and as a Now card when something stops (`docs/now.md`).
- **Agent tools** (`addons/phone/notification_tools.py`, the `phone` addon, on the acting user's notifications): `search_notifications`, `list_notifications`, `summarize_notifications`, `dismiss_notifications`, `snooze_notifications` (write).
- **Retention** (`notifications/retention.py`): `NOTIFICATION_RETENTION_DAYS` (30), every 6 h, per user; task-linked rows and accepted/dismissed suggestions are kept.
- **App icons** (`app_icons.py`): the phone saves each app's icon from its notifications and uploads it, so the web shows the real icon next to that app's notifications (Now rows, the Inbox's tiles). Files, not the database: `<data dir>/app-icons/<user id>/<package>.png` (`core.paths.APP_ICONS_DIR`; part of every backup with the rest of the data directory; removed with the user by `core.users.remove`). `GET /api/phone/app-icons` → `{icons: {package: hash}}` (the first 8 hex chars of the PNG's sha256; the phone uploads only missing or changed ones); `PUT /api/phone/app-icons/{package}` with the PNG bytes → 204, refused with 400 `bad_package` (not `^[A-Za-z][A-Za-z0-9_]*(\.[A-Za-z0-9_]+)+$` or over 200 chars), 400 `not_png` (by the signature and the IHDR: square, 48-192 px), 413 `too_large` (over 64 KB), 409 `too_many` (a new package past 500 per user); `GET /api/phone/app-icons/{package}.png` → the PNG (`Cache-Control: private, max-age=86400`, ETag = the hash, 304 on `If-None-Match`), 404 when the caller has none. The web asks with its session cookie (`<img src>`); a failed icon leaves the app's letter tile and is not asked for again until the page reloads.

## Direct push to the phone (`addons/phone/push.py`)

Everything the server shows on the phone goes this way; Home Assistant is no part of it, and no source of the location / car / wake signals either (the phone app is: `docs/signals.md`).
- `send(user, type, data)` stores the event for `user` in `phone_events` (one AUTOINCREMENT `seq` for the server, never renumbered; per-type expiry `TTL`: alert 15 min, notification_action 120 s, otp_request 4 min, suggestions 6 h, reminder 12 h, notify 24 h; rows older than 2 days deleted) and pings every one of **that user's** devices registered in `phone_push` with a ping carrying **only** `{"seq": "<n>", "type": "<type>"}` (`push.ping_data`), on the device's transport. Without the `phone` addon nothing is stored or pinged (returns False). The app fetches `GET /api/phone/events?after=<seq>` with its device token and gets only its user's events (`latest` = their newest seq) — no content goes through the push service, and a lost ping only delays an event (the app also catches up on start and on every notification sync). Expired events are never returned, so an old urgent alert can't pop up late.
- **Transports** (each registration's `transport`, its `address`):
  - `unifiedpush` — the endpoint a UnifiedPush distributor app on the phone (ntfy; the public ntfy.sh by default, or your own ntfy server) gave the app; what prebuilt (release) apps use, and needs nothing on the server. A ping is a plain `POST` of the same JSON to the endpoint (aiohttp; headers `TTL` = the event's lifetime, `Urgency: high`), with a short timeout (8 s, 5 s to connect) and **no redirects followed** (a 3xx is a failure). 404 / 410 → that registration is deleted (the app was unregistered); 429 / 5xx retried once. The endpoint must be `https` (`http` only with `DANA_INSECURE_DEV=1`; there is no LAN allow-list), have a host, carry no user name or password and be at most 2048 characters (`push.check_endpoint`, again before every ping); a LAN host is allowed (your own ntfy), since the request is the fixed body and only its status is read. The endpoint is never logged or returned in full: only its host (`endpoint_host`).
  - `fcm` — an FCM token, for an app you build with your own Firebase project: a **high-priority FCM data message** with the same data (HTTP v1, OAuth via `google-auth`, token cached). `UNREGISTERED` / 404 / invalid token → that registration is deleted; 429/5xx retried once. Registering one on a server without `FCM_SERVICE_ACCOUNT_JSON` is refused (400 `fcm_not_configured`), never stored; FCM registrations left from before the key was removed are skipped (the self-check says so).
- Returns True when at least one device's ping was accepted (by FCM or the endpoint). Callers don't retry on False (the event is already queued; retrying would duplicate it). `notify(user, title, text, tag, channel)` is the `notify` event.
- Event types: `alert`, `suggestions`, `reminder`, `reminder_clear`, `notification_action`, `otp_request {request_id}` (a money sync waits for an SMS sign-in code: the app fetches the request and posts the code, docs/money.md), `notify {title, text, tag, channel: messages|important|digest}` (WhatsApp voice transcripts, the digest, `notify`-style alerts), `agent_sessions {sessions}` (below), `zones_changed {changed_at}` (the user's zones changed: the app re-registers its geofences, `docs/zones.md`). `send(..., replace=True)` deletes the user's earlier events of the type first: for events that carry the whole state.
- Endpoints (all for the caller, `phone` addon required): `POST /api/phone/register {transport: "unifiedpush", endpoint} | {transport: "fcm", token}` (+ `app_version?`) → `{ok, transport, latest_seq}` from a paired device (the request's own device, `core.auth.request_device`; a token of no device gets 400 `device_required`; refusals are 400 `{error: invalid | invalid_endpoint | fcm_not_configured, detail}`; the caller's newest seq: a fresh install starts from now; one registration per device and one per address: the same token or endpoint from another device, the app paired again or as someone else, moves the registration to it; the client never names a device id; deleting the device deletes its registration, `ON DELETE CASCADE`), `GET /api/phone/events` (from a paired device: `registered: false` when its registration is gone → it registers again; registrations silent for 60 days are dropped, the device stays), `GET /api/phone/devices` (`{fcm_configured, latest_seq, devices: [{device_id, name, kind, transport, endpoint_host, app_version, …}]}`: the caller's devices registered for push, never a token or an endpoint), `POST /api/phone/test` (a test notification on the caller's phone).
- Callers: task reminders and `reminder_clear` (`addons/tasks/triggers.py`, `core/now.py`, `core/weekly_review.py`), WhatsApp voice transcripts (`addons/whatsapp/events.py`, the connection's user), the briefing and meeting cards (`core/briefing.py`), the weekly review, suggestion pop-ups (`popups.py`), escalations / re-nudges, the digest, `notification_action` — each to the user it is about.
- UnifiedPush needs no setup on the server: the user installs ntfy on the phone and the app registers with it (`android/docs/notifications.md`). FCM, only for your own app build: a Firebase project's service account with the role `firebasecloudmessaging.admin`, its JSON key in `FCM_SERVICE_ACCOUNT_JSON` (secret store only); the app's `google-services.json` comes from the same project (`android/docs/release.md`).
- Tests: `bin/test test_unifiedpush` (registrations per device and user, endpoint checks, pings through a fake ntfy server), `bin/test test_phone_users` (FCM, events, catch-up per user).

## Coding-agent sessions (`addons/phone/agent_sessions.py`)

The user's Claude Code and Codex sessions on their laptop, live on the phone (Android 16 Live Updates; the phone side is in the Android repo's `docs/notifications.md`).
- **Laptop**: `bin/dana-agent-hook claude|codex` is a global hook of both agents (`~/.claude/settings.json`: `UserPromptSubmit`, `PreToolUse`, `PostToolUse`, `PermissionRequest`, `Notification`, `Stop`, `StopFailure`, `SubagentStart`, `SubagentStop`, `SessionEnd`; `~/.codex/hooks.json`: `UserPromptSubmit`, `PreToolUse`, `PostToolUse`, `PermissionRequest`, `Stop`), so terminal, T3 Code and Orca sessions all report. It trims the event to the fields the server reads (no tool output; prompt and last message cut short), sends it in the background with a user token from `~/.config/dana/agent-hook.env` (`DANA_URL`, `DANA_TOKEN`; `bin/dana users tokens issue USER --label agent-hooks`) and always exits 0 at once. Run by T3 Code (`T3CODE_THREAD_ID` set), it looks the thread up in T3 Code's state (`~/.t3/userdata/statev2.sqlite`, read-only) and adds `thread`, the thread's `title`, `parent_thread` (the root thread, `lineage.rootThreadId`, when this is a delegated child) and, when the env file sets `DANA_OPEN_URL` (a template with `{environment}` and `{thread}`, e.g. your T3 Code web address), `open_url` with the environment from `~/.t3/userdata/environment-id` and the root thread: tapping the notification opens that thread. Unset: no link.
- **Server**: `POST /api/agent-sessions/hook?agent=&host=&open_url=&thread=&parent_thread=&title=` → `record(user, agent, host, event)` keeps one row per session in `agent_sessions` (`<agent>:<session id>`): `running` (a prompt; `activity` from the tool call — "Editing push.py", a Bash call's description; `steps_done/steps_total` and the current step from TodoWrite / `update_plan`), `waiting` (permission request, permission notification, `AskUserQuestion` / `ExitPlanMode`), `done` (`Stop`; `summary` = the start of `last_assistant_message`), `failed` (`StopFailure`); `open_url` (https only; kept when a later event has none) is where the phone's tap goes. `SessionEnd` deletes it (with Claude's own subagents). `rev` rises with each status change. A T3 thread `title` is used over the prompt. **Subagents** are rows with a `parent` and show inside their parent's entry (`subagents`: title, status, activity, summary, steps), not as sessions of their own: Claude Code's own (their events carry `agent_id`; row `<parent id>/<agent id>`, `SubagentStart` / `SubagentStop`, titled by `agent_type`) and T3 Code delegated children (`parent` = `t3:<root thread>`, matched to the newest top-level session in that thread). The entry's `status` is the group's: waiting if anyone waits (a subagent turning to waiting raises the parent's `rev`, so the phone alerts), running while anyone runs ("Waiting for Gmail kind" when only subagents do), running for `GRACE` (90 s) after a subagent finished once the parent had stopped (the agent is woken with the result; a push follows when the grace ends), otherwise the parent's. A finished group is kept and pruned as one (a done parent stays while its subagents run); a subagent whose parent isn't listed shows on its own. Each change pushes the whole list (`snapshot`: running / waiting heard from in the last hour, done / failed of the last 15 min, newest first) as an `agent_sessions` event with `replace=True` — a status change at once, activity at most every `AGENT_SESSIONS_PUSH_INTERVAL` s (15) per user with a trailing push carrying the latest; the hook answers before the push goes out. `GET /api/agent-sessions` (the list), `DELETE /api/agent-sessions/{id}` (the phone's Hide, with its subagents; pushes the new list). All need `phone` and answer only for the caller.
