# Dana server — Agent Guide

The server of **Dana**, a personal assistant: aiohttp server + Telegram bot + web UI, one process (one pod), several users with their own addons. This file is the map; each area's details live in `docs/` — read the section you need of the matching doc before changing that area. **How to work fast** (the test loop, the local environment, parallel agents and their briefs, shipping): `docs/development.md`. Paths below are relative to `server/`; the repository map is `../AGENTS.md`.

## Clients

Clients of this server's payloads: the Android app / tablet / TV / watch (`../android/`, its own `AGENTS.md`; REST/SSE/WebSocket with a Bearer token), the web UI in `static/`, and the Raycast extension (`../extensions/raycast-assistant/`, its `README.md`). Change a payload only on purpose, and keep them in mind: a change that needs the app too lands in the same commit.

## Quick start

```bash
python3 -m venv .venv            # Python 3.12+ (3.14 is what the image and the tests run)
.venv/bin/pip install -r requirements.lock   # then always use .venv/bin/python (system python lacks deps)
cp .env.example .env  # required: only an LLM key (ANTHROPIC_API_KEY); optional: a transcription model (GEMINI_API_KEY / OPENAI_API_KEY, or WHISPER_URL: docs/configuration.md → Transcription), TELEGRAM_BOT_TOKEN
bin/test                       # the whole suite in parallel (~75 s on 16 threads; docs/development.md)
python main.py                 # run Telegram bot + web UI on :8080; a fresh database logs a setup link (docs/devices.md)
```

No linter/formatter/typecheck — only `pyrightconfig.json` (points to `.venv`). Python 3.14 is tested (the container, `Dockerfile`, and the local venv); 3.12+ is supported (no newer syntax or library). Dependencies: `requirements.txt` (direct) → `requirements.lock` (pinned, what the image installs; `docs/operations.md` → Dependencies). Run `git config core.hooksPath .githooks` once (from the repository root): pushing master then runs the tests first (`docs/operations.md`).

## Tests

- **`bin/test`** runs every script side by side and prints only failures (a failure is retried once alone and reported as flaky if it then passes). `bin/test --changed` runs only the scripts your diff touches or that import what it changed (seconds; use it while working), `bin/test shopping users` picks by name, `bin/test --quick` leaves out the slow import smoke test, **`bin/test --list` says what each script covers** (the first line of its docstring). Run the whole `bin/test` once before committing; the pre-push hook runs it again before a deploy (`docs/operations.md`).
- Scripts are standalone, **not** pytest: `test_*.py`, plus `test_web_*.mjs` for the web pages' pure parts (Node). Where they live: core tests in `tests/`, each addon's in `addons/<name>/tests/` (an installed addon's run with `bin/dana addons test PATH`); fixtures in `tests/fixtures/`; `bin/test` finds them all and runs each from `server/` with `server/` and `tests/` on `PYTHONPATH`. Each Python script starts with `import testenv; testenv.isolate("<name>")` before importing the app or LiteLLM (`tests/testenv.py`): LiteLLM does not load `.env`, every addon / identity env value is removed (a test sets fake ones itself), and the temporary database directory is removed at exit — real local credentials never reach a test database. In-process fakes shared by tests: `tests/testfakes.py` (`FakeHA`: Home Assistant REST + WebSocket; `FakeWAHA`: WAHA).
- A new script: `test_<area>.py` (in the addon's `tests/`, or `tests/` for core) with a docstring whose first line says what it covers — that is the list, there is none to update. Assert on data, not only on status codes. Per-user features get two users with the addon plus one without (isolation both ways, 403 `not_connected`).
- Captured fixtures, regenerated only on purpose: `WRITE_PARITY=1 bin/test test_parity` (the first user's tool lists and prompts, `tests/fixtures/parity/`), `WRITE_GOLDEN=tests/fixtures/golden.sse bin/test test_run_stream` (the web stream contract), `WRITE_WEB_FIXTURE=1 bin/test test_addons_api` / `test_shopping_users` / `test_money_page` / `test_live` (the web pages' payloads, the live activities' wire form). `tests/fixtures/db_8_1_0.sql` is a synthetic 8.1.0 database for migration tests.
- `bin/triage-eval` compares the notification triage judges (the model, TypeSafe) on the made-up set in `tests/fixtures/triage_eval.json`; not a test (it calls the real services, with their keys), not part of `bin/test`.
- An add-on repository's tests run against this server the same way: `cd server && PYTHONPATH=.:tests DANA_ADDON_DIRS=<its parent folder> .venv/bin/python <repo>/<addon>/tests/test_x.py` (the bank worker's `.mjs` tests live in the money_il add-on's repository).
- `tests/test_agent.py` runs the full ReAct loop against the real `MODEL` (needs its key); it is not part of `bin/test`: `PYTHONPATH=.:tests .venv/bin/python tests/test_agent.py`.
- **Local test environment** (Docker): `bin/local-env.sh up` builds the real image and starts it from the 8.1.0 database against stub services (`tests/local_env/`), `bin/local-env.sh test` runs the end-to-end rehearsal; with `DANA_LOCAL_SOURCE=1` it runs your working tree and `bin/local-env.sh restart` reloads a change in seconds → `docs/local-testing.md`. `scratch/` holds ad-hoc scripts (not tests).

## Architecture

- **Entrypoint** `main.py`: migrate, setup mode when there are no users and no `API_TOKEN` (`core/setup.py`: a one-time setup link in the log; the first admin is created in the browser; `docs/devices.md`), else users bootstrap, addons bootstrap (credentials key or generated key file + the first admin's default addons, once), the conversation core, the Telegram adapter, the aiohttp web server (port 8080) and its background loops.
- **Agent loop** `core/agent.py`: a custom ReAct loop over LiteLLM (no LangChain). Every call is streamed (`stream=True`, assembled with `litellm.stream_chunk_builder`); deltas and tool announcements are emitted as they arrive, a broken stream is retried, consecutive read-only tool calls run concurrently. The system message is the acting user's: their profile, the parts of the addons they have connected, cached per-turn sections (home map, About facts) and the date line.
- **Conversation core** `core/session_runner.py` (starts every run for an explicit `User`), `core/session.py`, `core/thread.py` (the shared `main` thread), `core/history.py` (pruning) — all keyed by user. **Runs** `core/runs.py`: each piece of agent work is a run with an in-memory event log; clients reattach with `GET /api/sessions/{id}/stream?run_id=&after=`, disconnecting never cancels, one run per session per user (409 `active_run`). Event types at the top of `core/runs.py`. **Model profiles** `core/models.py` (`fast` / `balanced` / `deep`).
- **Addons** (`addons/`, framework in `core/addons/`; design: `../docs/addons.md`): each addon is a package `addons/<name>/` — `addon.py` declares it as `addon = Addon("<name>", ...)` (credentials, settings, hooks such as `on_connect`, `prompt_parts`, `test`, `options`), `tools.py` its tools (`@addon.tool()`), every tool taking the user's `Connection` as first parameter `conn`, `hooks.py` its background jobs/event handlers/composer hooks, `api.py` its HTTP routes (`setup(app)`), `migrations/` its tables, `web/` its web pages (`web=(Page(...), …)`, registered with `static/dana.js`), `tests/` its test scripts. The loader (`core/addons/loader.py`) discovers official and installed addons (catalog, git commit or uploaded folder) automatically; `core/` never imports any addon (enforced by `tests/test_addon_hooks.py::test_core_imports_no_addons`). Tools are listed and run **for a user**, only from addons that user has connected (a user's instance of an addon is a **connection**: table `connections`, credentials encrypted with `CREDENTIALS_KEY`; `store.connect / update / disconnect / get / require`). Adding a tool: a function in the addon's `tools.py`; adding an addon: `bin/dana addons new <name> [--web] [--worker]` (writes `./<name>`; installed with `bin/dana addons install ./<name> --server URL`) or a folder in `addons/<name>/` → `docs/access.md` (Addon), `docs/writing-an-addon.md`. Each addon declares what it **needs** (`Need(kind, what, why, optional)`: env, account, hardware, app, region, addon; required addon needs are its `depends`) and what it **touches** (`Touches(hosts, acts_outside, stores_credentials, reads)`), shown before it is turned on or installed; `bin/dana addons table` writes the README's "What each feature needs" table from them. Running the server's addons (sources, the server-wide disable `core/addons/state.py`, the catalog and install `core/addons/catalog.py` / `install.py`, the restart `core/lifecycle.py`, the `bin/dana` CLI in `cli/`, the add-on kit in `cli/kit/`: `new`, `check`, `test`, `dev`, `publish`, `reference`) → `../docs/addons.md`; the catalog is its own repository, `dana-catalog`.

- **Database** SQLite through `core/db` (`get_db_connection()`); per-addon ordered migrations in `core/db/migrations/` and `addons/<name>/migrations/` (`mNNNN_<name>.py`, found by name, each docstring says what it changes), applied at startup after a snapshot → `docs/operations.md` (Database schema). Per-user CRUD helpers: `core/addons/data.py` (`UserTable`); SQL user-scoping lint: `tests/test_sql_scope.py`.
- **Devices** (`core/devices.py`, `core/devices_api.py`): each phone, watch, tablet, TV or browser is a device of one user with its own revocable token, made by pairing (a QR code or a short code); push registrations belong to the device (UnifiedPush through ntfy, or FCM for self-built apps); tablets and TVs pair from their first screen; the apps look for `_dana._tcp` on the LAN; setup mode (`core/setup.py`) creates the first admin, then the first-run wizard (`core/wizard.py`: you, Home, the model, your phone, add-ons, sample data) → `docs/devices.md`.
- **Zones** (`core/zones.py`, `core/zones_api.py`, `core/places.py`): each user's places (Home and others) live in Dana and drive location reminders through Dana's phone app (Home Assistant can import its zones) → `docs/zones.md`.
- **Users and access** (`core/users.py`, `core/access.py`, `core/auth.py`): every web request and Telegram update resolves to a `User`, bound as the current user (`users.acting_as`); sessions, runs, approvals, undo, learned phrases, usage and every background loop are per user. Levels `admin` / `member`; a tool the user lacks is refused like a made-up name; server-wide endpoints use `@requires(capability)`. Managing users: Settings → Household (`core/household_api.py`, `docs/household.md`), `bin/dana users`, `/api/addons*` and the web Addons page. A sample household (`core/demo.py`, `core/demo_api.py`, each addon's `demo.py`) loads and removes made-up demo users. Security rules (cross-user) → `docs/access.md`.
- **Web server** aiohttp, not FastAPI: `core/server.py` assembles the app (middlewares, `ROUTE_MODULES`, background loops); each route lives in the module that owns it — `core/<area>_api.py` (pages, sessions, assistant, debug, actions, now, briefing, usage, sharing, addons) or an addon's `addons/<name>/api.py`, each with `setup(app)`; static web shell in `static/` (`static/app-*.js` + `static/app.js`, `static/dana.js` SDK, `static/kit.css` shared screen kit; `static/app-panels.js` lists and mounts addon pages from `/api/addons`, `static/app-nav.js` + `static/app-places.js` draw the navigation (primary places, More, Edit: `docs/web-design.md`), `static/app-now.js` + `static/app-now-core.js` the Now screen the app opens on (`docs/web-design.md`, "Now"), and each addon page lives in `addons/<name>/web/`). **Telegram** `core/telegram_bot.py` (aiogram): a channel adapter over the core. **Proactive messages** `core/notify.py` (Telegram); phone push `addons/phone/push.py`; **live activities** `core/live.py` (`docs/live.md`).
- **Composers** (`core/composers.py`): Now (`core/now.py`), wake (`core/wake.py`), briefing (`core/briefing.py`), weekly review (`core/weekly_review.py`), search (`core/search.py`), self-checks (`core/checks.py`), context chats, dashboards (addon widgets: `core/dashboard.py`) — each works for one user from the addons they have → `docs/now.md`, `docs/people.md`, `docs/dashboard.md`.
- **Agent actions**: reversible writes run at once with Undo (`core/undo.py`); only `confirm` tools ask; learned phrases (`core/shortcuts.py`); on-screen context (`core/device_screen.py`) → `docs/agent-actions.md`.
- **LLM calls**: every non-chat call goes through `core/llm.py` (`complete()`, `complete_json()`, `transcribe()`, pass `purpose=`), one model env var per job; the provider (Claude, OpenAI, Gemini, Ollama) and its key are chosen in Settings → The model (`core/llm_provider.py`, stored in `server_settings`: `core/server_settings.py`), env overrides → `docs/configuration.md`. Realtime voice (`core/realtime.py`, OpenAI's protocol) is the one exception. **Usage and cost** `core/usage.py`; `core/budget.py`: the monthly budget pauses background purposes → `docs/usage.md`. **Signals** (wake, screen, car, location, sleep, weather) come from ranked sources, the phone app first (`core/signals.py`, `core/wake_window.py`) → `docs/signals.md`.
- **Persona**: the assistant is **Dana**; the prompt is the acting user's (`core/user_profile.for_user(user)` for their name / pronoun / context), and an addon's words live in its `addon.py`.
- **Android app updates**: the server offers the phone / watch APKs (`core/app_updates.py`, `/api/app/*`) from the latest GitHub Release of `APP_RELEASES_REPO` (checked every 6 h) and from uploads (`android/bin/deploy-app.sh`), the newest `versionCode` winning → `docs/operations.md` (App updates).

## Key conventions

- `@addon.tool()` (in the addon's `tools.py`) auto-generates the OpenAI-compatible JSON schema from Pydantic type hints + Google-style docstrings; the first parameter is always `conn: Connection` (left out of the schema). Code that calls a tool function directly passes `store.require(user, "<name>")`.
- Only `confirm` tools return `{"status": "pending_approval"}` (Approve/Deny in the app, web and Telegram); every other write runs at once and registers an undo (`core/undo.py`, `POST /api/undo/{id}` in `core/actions_api.py`). A tool the user does not have never asks (refused like an unknown name).
- `is_write` / `confirm` / `acts_outside` flags are given to `@addon.tool`; `registry.needs_confirmation(name, args)` (`core/addons/registry.py`) decides in the agent loop. `untrusted_result=True` marks a tool whose result is text written by other people (mail, messages, notifications, calls, web, …): the model reads it framed by `core.text.untrusted`, and for the rest of that turn `acts_outside` tools ask first; wherever others' text enters a prompt without a tool, frame it with `core.text.untrusted(source, text)` (a frame in a turn's context or message taints it from the start; `docs/agent-actions.md`, "Text written by others").
- `escape_markdown()` from `core.text` required for Telegram-safe strings.
- **Schema**: only through a new migration in `core/db/migrations/` (never `CREATE TABLE` / `ALTER TABLE` in a module, never at import time).
- **Addon config**: whose account / which entities belongs to the user's connection (credentials encrypted, settings JSON); server-wide settings stay in env. Nothing reads an addon's account from env: connections are made on the Addons page, with `bin/dana` or the API.
- **Time**: the container runs in UTC. Never call `datetime.now()` for anything user-facing — use `core.clock.now()` (aware, user's zone), `clock.from_timestamp()`, and `clock.describe_now()` for prompts. One zone for the server: `TIMEZONE` env → the first-run wizard's server setting → `TZ` → UTC (resolved once at startup).
- **Data paths**: everything persistent lives in the directory holding the DB (`core/paths.py`: `recordings/`, `media/`, `uploads/images/`, `app-updates/`, `app-icons/` (each user's app icons, `addons/phone/app_icons.py`), `snapshots/`, `backups/` (the default backup destination), `.backup-work/` (a download being built)). **Backups** (`core/backups.py`, `core/backups_api.py`, `cli/backups.py`): Settings → Backups, a schedule into a destination folder, Download backup, `bin/dana backups restore` → `docs/backups.md`. In k8s that is the PVC at `/app/db`; never write state elsewhere — it is lost on restart.
- **Tool results** are capped at `MAX_TOOL_RESULT_CHARS` (`core/agent.py::limit_tool_output`) and stored history at 40 messages / `MAX_HISTORY_CHARS` (`core/history.py::prune_history`, applied by `session.append_history`).
- **User context**: a tool runs only through `registry.execute(user, name, args)` (the run's / request's / handler's user, or `users.current()`), which refuses tools of addons that user has not connected (`registry.ToolNotAvailable`); decide anything about a tool call (asks? write?) only after `registry.has_tool(user, name)`. A handler that calls a tool function directly passes `store.require(user, "<name>")` and lets `NotConnected` reach the middleware (re-raise it before a catch-all `except`). Server-wide endpoints get `@requires("<capability>")`; never compare access level names in code. Shareable items go through `core/addons/sharing.py` (register an `ItemType`; lookups add `shared_ids`, writes check `access`, payloads add `shared_by` / `access` only for shared items). New background work takes a `User` and binds it with `users.acting_as`; never look up the first admin (`users.first_admin()` only for the env token / dev mode, the open Telegram bot, the server timezone, bootstrap / migrations, startup logging). A prompt about a user takes their words from `user_profile.for_user(user)`, never a name or pronoun in the text.
- **Web auth** (`core/auth.py`): every request needs `Authorization: Bearer <token>` (a device's or user's DB token, or `API_TOKEN` when set) or the `/login` session cookie, and gets `request["user"]`; except public paths (`/login`, `/api/health`, `/api/app/*`, `/api/pair`, `/api/setup*` (both prove themselves with a rate-limited code), `/static/*`, `/sw.js`, `/manifest.json`) and `/webhook/waha`, which takes no token but only events WAHA signed with `WAHA_WEBHOOK_SECRET` (no user set; the `Host` header is never trusted). No `API_TOKEN`: setup mode until the first admin exists (only `/setup`, the setup API, the health check and static files answer; everything else 503 `setup_required`), then DB tokens only; `DANA_INSECURE_DEV=1` (local development) makes every request the first admin and listens on 127.0.0.1 only.

## Deploy (summary — details in `docs/operations.md`)

- Commit, `git push origin master` → the pre-push hook runs `bin/test` (a failure stops the push), nothing more. A release: bump VERSION and the app versions, push the tag `v<version>` (release.yml publishes `ghcr.io/ronganam/dana:<version>`), then `bin/deploy <version> --wait` (GitOps or compose, from the site's `deploy.env`; installed add-ons' workers pinned through `$DANA_EXEC dana addons workers --json`); verify after that.
- Config: env vars listed in `docs/configuration.md`; secrets never get printed or committed.
- Production debugging (logs, DB inspection without sqlite3, API endpoints): `docs/operations.md`.
- A deployment's own setup (where it runs, its secret store, devices, the add-ons it installs) lives in its site, never in the repository: read `../site/AGENTS.md` when it exists.
